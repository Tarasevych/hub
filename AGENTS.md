# AGENTS.md — єдині правила для всіх ШІ-агентів Mijn Ruimte · één regelset voor alle AI-agenten

**Статус · status:** канонічне джерело правил (ORCH-001). Версія правил: див. `orchestratie/beleid.json → regelsVersie`; відбиток — `orchestratie/regels.lock.json`.
`CLAUDE.md`, `GEMINI.md`, `.cursorrules` тощо — лише перехідники, що вказують сюди. Якщо інший документ суперечить цьому файлу — чинний цей.
Dit is de canonieke bron. Adapters (`CLAUDE.md`, `GEMINI.md`, …) verwijzen hierheen. Bij tegenspraak geldt dit bestand.

Зміна правил = запис у `orchestratie/BESLUITEN.md` + вища `regelsVersie` + `node scripts/orch.mjs vergrendel`. Інакше `orch controleer` падає.

## 0. Головний принцип · Hoofdprincipe

Одна пам'ять проєкту, одна система правил, одна інтеграційна черга, один узгоджений випуск — незалежно від кількості й типу агентів
(Claude, Antigravity, AutoClaw, ChatGPT, Codex, Grok, GitHub Copilot, Microsoft Copilot, Gemini, Cursor, Windsurf, Cline, Devin, OpenCode та майбутні).
Één projectgeheugen, één regelset, één integratiewachtrij, één afgestemde release — hoeveel en welke agenten er ook zijn.

## 3. Під час роботи · Tijdens het werk

- Власна гілка `feature|fix|audit|release/<тема>-YYYYMMDD-HHMMSS` від базової фіксації змін. Один Task ID (`ABC-001`) на задачу; він у назві гілки, фіксації змін, PR, пакеті.
- Ніколи не пиши в чужі гілки, `voornaamst`, `integratie`, `release/*`. Ніколи не примусового відправлення, не переписуй історію, не видаляй резервні копії.
- Тихе перезаписування чужих змін заборонене: при конфлікті — перенесення бази на інтеграційну гілку, конфлікти розв'язати явно, згадати в звіті.
- Виявив стару помилку — виправ (окремою фіксацією змін), не ігноруй. Нічого не прибирай «щоб запрацювало»: кнопку, вкладку, тест, перевірку.
- Секрети, маркери доступу, приватні ключі, вміст листів — ніколи в чат, журнал, фіксація змін чи пакет. Приватні ключі власника агентам не передаються.
- Робоче середовище, основна гілка, резервні копії, критичні дозволи — тільки після явного погодження власника (не іншого агента).
- Логотипи (REESTR-LOGO-001): лише з реєстру `src/merk/` (`<Merk>`, `MerkLogo`); новий знак — через `scripts/merk-officieel-maken.mjs`, без копій `<svg>`. Деталі — §6. · Elk logo uit het ene merkregister.
- База сповіщень і дій (MELDINGEN-REGISTER-001, B-026): кожна нова служба чи код дії сервера обов'язково отримує людську назву `[uk, nl]`, предметну категорію (без `overig`) і схему доказів у `shared/beheer-journaal.ts` / `shared/meldingen-catalogus.ts`, а технічний шум — фільтр у `RUIS_PATROON`; перевіряє `node scripts/meldingen-register-controle.mjs` (§11).
- Діагностика й час власника (B-009): не просити власника вручну виконувати команди в терміналі (`df -h`, `journalctl`) чи вручну збирати пакети; без доступу до `<VM-IP>` дати стислий висновок (1–2 речення) для інфраструктурного агента на ПК власника. Не вгадувати причину збою `voorcontrole` (не списувати на `.zip`, якщо `structuur` пройдено). Деталі нижче, B-009.

## 3а. Авторство, досьє, навички · Auteurschap, dossiers, vaardigheden (BIJDRAGE-001, деталі — §9)

- Кожен внесок — запис `orchestratie/bijdragen/<ID>/…json` (`orch bijdrage`): людина, що доручила; агент, платформа, конкретна модель; що, чому, на чиїй роботі. Записи лише доповнюються.
- Перед зміною функції — її досьє `orchestratie/onderwerpen/<назва>.json`; доповни його. Можливості не видаляй: утрачене — `verloren` і поверни.

- Перед видаленням гілки чи закриттям запиту без злиття — `orch verwijzing` (хто, чому, остання фіксація змін, куди ввійшло), щоб посилання не вело в «404» (§9.7).

## 3б. Екосистема «Плющ» та архітектурна перевірка · Ecosysteem «Klimop» en architectuurcontrole (KLIMOP-001, деталі — §10)

- **Головний принцип розподілу повноважень:** жоден окремий учасник, пристрій, сервер, ключ, адміністратор, постачальник чи ШІ-агент не має одноосібної необмеженої влади над усією екосистемою; права власника особистих даних, оператора вузла та зміни спільних правил відокремлені; випадкова більшість вузлів не отримує критичних прав; самовільне розростання («комп'ютерний хробак») заборонене.
- **Обов'язкова 15-пунктова перевірка кожної зміни (§10.4):** перед створенням чи зміною складника перевір відсутність нової єдиної точки відмови, прихованих повноважень, зайвих метаданих, примусових витрат ресурсів чи ризику для всієї мережі через один з'єднувач, а також збереження законного відновлення, відкликання дозволів, сумісності вузлів, ізоляції збоїв, захисту людини, перевірюваності та безпечного повернення стану.
- **Заборонені спрощення (§10.5):** не називати систему абсолютно невразливою; не вважати копії на одному сервері незалежними вузлами; не плутати поділ секретів Шаміра з поділом великих файлів (де потрібне шифрування + коди відновлення втрачених фрагментів); не прирівнювати пороговий підпис до шифрування чи звичайне серверне шифрування до повного нерозголошення; не вимикати чинні сервери й PostgreSQL до доведеної готовності незалежної заміни; не підміняти перевірені протоколи власними неперевіреними алгоритмами.
- **Порядок дій (§10.6):** Етап 0 (повний аудит дійсного стану; наявність файла в репозиторії ≠ робота наживо) → Етап 1 (цільова специфікація «Плющ») → порівняння технологій → поетапний план випусків → ізольовані випробування. Робочу інфраструктуру без окремого затвердження власника не змінювати.

## 4. Перед передаванням результату · Vóór overdracht

1. Усі зміни зафіксовано. `node scripts/orch.mjs versheid --taak <ID> --fase overdracht` — зелене (база не застаріла з перетином файлів, правила чинні).
2. Тести: `node scripts/eenheidstests.mjs <фільтр>`, `npm run typecheck:server` (де можливо). Результати — у `TESTRESULTATEN` (формат v2) і звіті.
3. Передача будь-яким каналом з `beleid.json → inlevering.kanalen` (PR, MCP, HTTP API, локальний файл, ZIP, TAR.GZ, git patch, вебзавантаження),
   але завжди з `ORCH-OVERDRACHT.json`: taakId, agent, basisCommit, regelsVersie, regelsHash, samenvatting, список змінених файлів, тести.
   Приймає все один конвеєр: `node scripts/orch.mjs inleveren --bron <файл|тека|гілка>` — нова гілка від бази, зміни, конфлікти з `integratie`
   (`git merge-tree`), тести, запис у `orchestratie/inleveringen/`, черга. Передача, що змінює файли стану (`orchestratie/taken`, `inleveringen`,
   `wachtrij.json`, `regels.lock.json`, `geinstalleerd.json`), відхиляється — їх пише лише `orch` або власник. Єдиний виняток — власний
   `orchestratie/taken/<ID>.json` (декларація агента з `taak-start`); при злитті лишається версія `integratie` (`.gitattributes` → `merge=orch-staat`).
4. Звіт українською: 1-м рядком — пряме посилання на `mijn-ruimte-<versie>.tar.gz` (окремо від `-overdracht.zip`); далі — що готово, що перевірено (фактично, не за метаданими), де результат, що наступне, що свідомо не зроблено.
5. Статус задачі: `in_progress` → `ter_integratie` (передано) → `integrated` (злито в `integratie`) → `released` (пакет зібрано) → `installed`
   (встановлено встановлювачем на сервері). Статус змінює лише той крок, що його здійснив; агент не ставить `installed` сам.

## 5. Інтеграція та випуск · Integratie en release

- Одна послідовна черга: `orchestratie/wachtrij.json` (FIFO за базою; `wachtrij volgende|klaar|terugtrekken`, лише одна задача `bezig`).
  Злиття в `integratie` — завжди `--no-ff`, без force; конфлікт → `klaar --uitkomst afgewezen`, задача повертається агентові на перенесення бази.
- Пакет на застарілій базі (basisCommit не предок `integratie`, перетин файлів) не випускається й не встановлюється.
- Режими встановлення (`beleid.json → kritiek.installatieModi`): `handmatig`, `na_bevestiging` (Passkey/підпис власника; типовий),
  `automatisch_beperkt` — лише за окремо затвердженою й підписаною політикою. Зараз дозволені перші два.
- Критичні політики (`kritiek`) чинні лише з підтвердженням власника в `orchestratie/regels.lock.json → eigenaar`: підпис SSH (`orch bevestig`)
  або passkey на сайті (`eigenaar.soort = passkey`, запис у root-журналі); до того — «пропозиція».
- **TRACE-001 (з 20261103-211555):** обов'язковий `ONTWIKKELARCHIEF.json` і підтверджена точна GitHub Release-asset SHA-256. Журнал зафіксовано, сервер і root відхиляють відсутнє, неправильне чи недоступне. Детальні умови нижче, B-007, deploy/ПРАВИЛА-ПАКЕТА-РОЗГОРТАННЯ.md §7.

### Повні умови випуску, журналу й перевірок (§5)

- Зміна правил власником без SSH: сайт `mcp.tarasevych.com/agents` → «Координація» → редагування файлів правил → перевірка пропозиції (`regelsVersie`
  вища, запис у `BESLUITEN.md`, `beleid.json` дійсний) → ключ доступу (рішення `orch-regels`; root лише фіксує підтвердження у своєму журналі) →
  гілка `regels/<versie>-<час>` з новим lock і `CONTEXT-COMPACT.md` іде в `origin`. Злиття в `integratie` — лише власник. Сайт/MCP/HTTP викликають
  ті самі функції, що й CLI (`inleveren`, `beoordeelVoorstel`, `vergrendel`) — окремої логіки немає (`beleid.json → site`).
- **TRACE-001 (з випуску 20261103-211555):** кожен пакет містить `ONTWIKKELARCHIEF.json` із посиланням на `orchestratie/ontwikkelarchieven/<TASK-ID>.json` у тій самій фіксації змін на GitHub і посиланням на випуск `.tar.gz`. Журнал зберігає доступні тексти запитів, покрокові дії та спроби, фіксації змін, результати тестів, вкладення з посиланнями й хешами, тимчасові артефакти (або факт їх відсутності), обґрунтування рішень, компроміси й невиконане; не містить приватних ключів, маркерів доступу, вмісту пошти чи прихованих внутрішніх міркувань моделі. Дані з обмеженим доступом — лише опис і хеш без вмісту. Після складання файл випуску `mijn-ruimte-<versie>.tar.gz` публікують у GitHub Release з тегом версії. Серверна передперевірка і root-встановлювач окремо перевіряють незмінну фіксацію змін, її походження з вказаної гілки, SHA-256 журналу і точний SHA-256 архіву на GitHub; відсутність, помилка посилання, невідповідність чи недоступність GitHub **обов'язково блокують встановлення**. Жодних винятків «продовжити без перевірки» немає. Старіші пакети не змінюються. Потребує затвердження правил власником Ключ доступу/SSH і злиття у захищену інтеграцію.
  TRACE-001: elk nieuw pakket heeft een commitgebonden dossier én een werkelijk geüploade Release-asset met identieke SHA-256. De site en root weigeren bij ontbrekende, ongeldige of onbereikbare GitHub-herkomst. Geen geheime gegevens of verborgen modelredenering.
- Випуск збирає лише `node scripts/orch.mjs pakket --taak <ID> --auteur "…" [--manifest …] [--testresultaten …] [--sig …]`: сумісний
  `mijn-ruimte-<versie>.tar.gz` (через `deploy/uitrol/maak-voorstelpakket.sh`, з файлом `UITROL-BASIS` = встановлена версія + commit + відбиток
  правил) і пакет передачі `mijn-ruimte-<versie>-<agent>-overdracht.zip` (архів, `.sha256`, `ORCH-OVERDRACHT.json`, `UITROL-MANIFEST.json`,

## 8. Що свідомо не є правилом · Wat géén regel is

Старі операційні інструкції і документи змін лишаються довідкою про те, як працює код. Вони не додають правил понад цей файл і не скасовують його.
Якщо в них знайдено суперечність — виправити документ або додати рішення в `BESLUITEN.md`, а не мовчки обрати одне з двох.

## 9. Авторство, історія функцій і навички · Auteurschap, functiegeschiedenis en vaardigheden (BIJDRAGE-001, з 18.11.2026)

**Навіщо.** Над однією функцією працюють різні агенти й моделі, часто ізольовано один від одного. Без обліку агент бачить чужі зміни, вважає їх помилкою, переробляє заново, витрачає ліміти й час і губить напрацювання попередників. Тепер кожен, хто бере роботу, бачить, **хто, якою моделлю, що, чому й на чиїй роботі** зробив, і хто працює паралельно.
*Waarom:* verschillende agenten en modellen werken aan dezelfde functie. Zonder registratie lijkt ander werk een fout en gaat het verloren.

### 9.1 Старт сеансу — сам, без нагадувань

1. `node scripts/orch.mjs begin --agent <id> [--taak <ID>] [--onderwerp <назва>] [--tekst "<завдання>"]`. Команда нічого не змінює в git і показує: чинність правил; перелік навичок і завантажує їх у теку агента (`beleid.json → vaardigheden.spiegels`, для Claude — `.claude/skills/`); досьє функцій, що стосуються завдання (за словами задачі й зміненими файлами); внески за задачею; незавершені паралельні задачі тієї ж функції.
2. Claude Code запускає `begin --kort` автоматично на старті сеансу (`.claude/settings.json`, подія SessionStart). Інші агенти виконують команду першим кроком (§2.0); їхні перехідники вказують сюди.
3. Перш ніж створювати щось нове, добери навичку: `node scripts/vaardigheden/kies.mjs "<завдання>"`, і прочитай досьє: `node scripts/orch.mjs onderwerp <назва>`.

### 9.2 Облік авторства в кожній гілці й запиті на злиття

- Запис: `node scripts/orch.mjs bijdrage --taak <ID> --agent <id> --platform "<Claude Code | Google Antigravity | …>" --model <конкретна модель> --opdrachtgever "<людина>" --soort <вид> --wat "<що>" [--waarom "<чому>"] [--bouwt-voort-op <id запису>] [--voorganger "<опис роботи без запису: гілка, фіксація, PR>"] [--onderwerp <назва>] [--pr <N>]`.
- Види: `begin`, `nieuw`, `herwerkt` (переробив), `afgerond` (доробив), `overname` (перейняв), `samenvoeging` (об'єднав), `herstel` (повернув утрачене), `controle`, `correctie` (виправив попередній запис). Для переробки, доробки, перейняття, повернення, об'єднання й виправлення обов'язкові «чому» і «на чому будує».
- Модель — конкретна (`claude-opus-5-5`, `claude-fable-5-2`, «Gemini 4 Hydrogen (high)»), не лише «Claude» чи «Gemini». `model.bron`: `omgeving` (підтвердило середовище), `auteur` (заявив агент), `eigenaar` (сказав власник).
- Мінімум один запис на задачу; `versheid --fase overdracht` без нього червоне. Записи **не редагують і не видаляють** (`orch behoud`): помилку виправляють новим записом `correctie` (зокрема з полем `corrigeert`, що уточнює модель виконавця й зберігає первинне значення у `eerderGeregistreerd`). Кожен запис — окремий файл, тож паралельні гілки не конфліктують, а злиття нічого не губить.
- У тексті запиту на злиття — розділ «Хто що зробив» з тими самими відомостями (людина, агент, модель, вид, причина). Фіксації змін можуть мати рядки `Bijdrage-Agent:` / `Bijdrage-Model:`; джерелом правди лишається файл обліку.
- Пакет випуску (`orch pakket`) бере всі нові записи від установленої версії у `BIJDRAGEN.json` і в `UITROL-MANIFEST.json → bijdragen` та доповнює `deelnemers`; сайт показує їх у згорнутому блоці «Хто що зробив» біля учасників випуску.

### 9.3 Досьє функції — уся історія в одному місці

- `orchestratie/onderwerpen/<назва>.json`: назва й опис, слова для пошуку, файли функції (`paden`), усі задачі/гілки/запити на злиття з агентом і моделлю (`werk`), можливості з незмінним `id`, походженням і станом (`actief`, `in-ontwikkeling`, `verloren`, `vervangen` + `vervangenDoor`, `ingetrokken` лише за рішенням власника), зауваження власника, відкриті питання.
- Хто змінює файли з `paden`, той доповнює досьє в тій самій гілці. Записи роботи, можливості й зауваження **не видаляють** — лише змінюють стан із причиною (`orch behoud` стереже).
- Переробляючи функцію, спершу звір перелік можливостей: нова версія має містити всі `actief`; що не вдалося перенести — `verloren` з причиною й наступним кроком.

### 9.4 Зауваження власника — покращення конкретної речі

«Мені не подобається X» означає: не подобається саме X (вигляд, поведінка, місце кнопки), а не вся функція. Запиши в досьє `opmerkingenEigenaar`: `betreft` (що саме), `uk` (суть словами власника), `behouden` (що лишається). Змінюй лише `betreft`; решту можливостей зберігай. Не заміняй цілий складник новим «з нуля», якщо власник цього прямо не сказав.

### 9.5 Навички — одне джерело, злиття без утрат

- Канонічне місце — `.agents/skills/<назва>/SKILL.md` + запис у `scripts/vaardigheden/catalogus.json` (версія SemVer, `mogelijkheden` з незмінними `id` і полем `agenten` — хто підтримує; зокрема спільні для всіх 14 агентів `movnyi-zakon` та `klimop-architectuur`). Окремих копій навичок у теках агентів не ведуть: дзеркало генерує `begin`/`vaardigheden-spiegel`, воно позначене `.gespiegeld.json` і не потрапляє в git.
- Створив навичку — збережи її там же на гілці `feature/vaardigheid-<назва>-<РРРРММДД-ГГХХСС>` (або у своїй гілці задачі), з записом обліку, і вона піде в спільний випуск. Навички з облікового запису власника (claude.ai тощо) переносять сюди з полем `ookBekendAls`.
- Злиття навичок: версія не зменшується, навички й можливості не зникають. Якщо агент не підтримує опцію, її **не видаляють**, а позначають у `agenten`. Вивести з ужитку — лише рішенням власника (`ingetrokken`, `ingetrokkenMogelijkheden`).
- Перевірка: `node scripts/vaardigheden/valideer.mjs`, `node scripts/orch.mjs behoud --tegen <база>`.

### 9.6 Історія не губиться

Злиття лише `--no-ff`, без стискання й переписування історії. Попередні випуски, гілки й запити на злиття лишаються; закривають їх із поясненням, куди увійшло. Якщо людина помітила втрату — знайди за досьє й обліком, хто і в якій гілці її мав, познач `verloren` і поверни (`herstel`).

### 9.7 Посилання без «404» (VERWIJZING-001)

На сторінці оновлень кожна гілка, запит на злиття, міграція й задача — рядок із людською назвою, підсумком і станом («відкрито», «злито», «закрито», «гілку видалено»), а не голий номер. `orch pakket` збирає це сам з історії git і реєстру `orchestratie/verwijzingen/` у `UITROL-MANIFEST.json → verwijzingen` та `BIJDRAGEN.json`, тому видно й без GitHub. Переглянути заздалегідь: `node scripts/orch.mjs verwijzingen --sinds <база>`.

1. Перед видаленням гілки: `node scripts/orch.mjs verwijzing --soort tak --id <гілка> --gebeurtenis verwijderd --wie "<хто>" --waarom "<чому>" [--opgenomen-in "№N"]` — остання фіксація змін підставиться сама, за нею гілку можна відновити.
2. Закриваючи запит без злиття: `--soort pr --id <N> --gebeurtenis gesloten --opgenomen-in "<куди ввійшло>" --waarom "…"`.
3. Людську назву й підсумок, якщо повідомлення злиття їх не дає: `--gebeurtenis beschrijving --titel "…" --samenvatting "…"`.
4. Записи лише доповнюються. Гілка, якої немає ні в сховищі, ні в історії злиттів, ні в реєстрі, дає попередження `VERWIJZING_ONVERKLAARD` під час збирання випуску.

## 10. Цільова жива цифрова екосистема «Плющ» · Levend digitaal ecosysteem «Klimop» (`KLIMOP-001` / `B-024`, з 20.11.2026)

Повний двомовний текст маніфесту: [`docs/hub/АРХІТЕКТУРНИЙ-МАНІФЕСТ-ПЛЮЩ.uk.md`](docs/hub/АРХІТЕКТУРНИЙ-МАНІФЕСТ-ПЛЮЩ.uk.md) · [`docs/hub/ARCHITECTUURMANIFEST-KLIMOP.nl.md`](docs/hub/ARCHITECTUURMANIFEST-KLIMOP.nl.md). Досьє пам'яті: [`orchestratie/onderwerpen/ecosysteem-klimop.json`](orchestratie/onderwerpen/ecosysteem-klimop.json). Навичка: [`.agents/skills/klimop-architectuur/SKILL.md`](.agents/skills/klimop-architectuur/SKILL.md).

### 10.1 Статус та межі дозволу

- Маніфест «Плющ» є **цільовою архітектурною концепцією** перебудови платформи від моделі «один головний сервер → спільне ядро → центральна база → усі служби» до моделі «незалежні вузли ↔ захищена мережа ↔ розподілене зберігання ↔ ізольовані служби ↔ незалежне керування».
- **Він НЕ є дозволом на негайну зміну робочої інфраструктури.** Чинна база PostgreSQL, сервери, резервні копії, 11 піддоменів, приватне сховище М7, ключі доступу, історія змін і затверджений порядок роботи агентів зберігаються без жодної втрати даних чи можливостей (§3.2, §35 маніфесту).
- Наявність програмного складника в репозиторії **ніколи не прирівнюється** до фактично впровадженої та перевіреної наживо можливості (§3.3).

### 10.2 Сім структурних елементів, вузли, захист даних і людини

1. **Сім елементів екосистеми (§1):** **Коріння** (незалежні основи довіри без одноосібної влади), **Стебла** (автентифіковані зашифровані зв'язки з альтернативними маршрутами й від'єднанням пошкоджених ділянок), **Листя** (ізольовані функціональні складники), **Вусики** (авторизоване, обмежене й відкличне розширення без самовільного встановлення), **Живлення** (добровільний і прозорий обмін ресурсами без примусу), **Імунна система** (спостереження без розкриття приватного вмісту, самовідновлення в межах правил і поступове поширення оновлень), **Насіння** (переносність і відтворення екосистеми без єдиного творця).
2. **Чотири типи вузлів (§4):** постійні незалежні (різні середовища й ризики відмови), особисті пристрої користувачів, спеціалізовані з обмеженими правами та перехідні вузли долучення (не єдиний шлях виявлення). Сусідній вузол ніколи не вважається довіреним лише через мережеву близькість (§5).
3. **Сім рівнів шифрування та криптографія (§6–§13):** пристрій → дані (`AES-256-GCM` / `ChaCha20-Poly1305`) → передавання → зберігання (шифрування + коди відновлення втрачених фрагментів) → повноваження → відновлення → порогове управління. Поділ секретів Шаміра (§7), перевірюваний поділ Фельдмана/Педерсена (§8), проактивне оновлення часток за криптографічними епохами (§9) та порогові підписи ФРОСТ (§10) застосовуються за своїм прямим призначенням з версіонуванням криптографічних форматів і підготовкою до стандартизованої постквантової криптографії (§13). Для групових повідомлень оцінюється стандарт 9420 (§12).
4. **Захист людини та 7 категорій спільного керування (§14–§20):** незалежні процедури для втрати пристрою/ключів, хвороби, тривалої відсутності, спадкування та фізичного чи психологічного примусу (без автоматичного знищення особистих даних при підозрі на примус, §15–§17); 7 розмежованих категорій повноважень (власні дані, особисті пристрої, операційне керування вузлом, супровід коду, криптографічне підтвердження критичних змін, надзвичайне відновлення, зміна правил усієї екосистеми) та часові затримки для особливо ризикових рішень без уповільнення щоденної пошти, файлів чи календаря (§19–§20).

### 10.3 Шістнадцять спеціалізованих напрямів відповідальності агентів (§32–§34)

1) загальна архітектура; 2) міжвузловий зв'язок; 3) криптографія; 4) розподілене зберігання; 5) ідентичність; 6) відновлення; 7) захист людини; 8) система спільного керування; 9) з'єднувачі зовнішніх служб; 10) самовідновлення; 11) захист випусків; 12) перевірка безпеки; 13) швидкодія та ресурси; 14) приватність; 15) сумісність і перенесення; 16) документація та супровід. Жоден агент не може одноосібно створити, затвердити й встановити критичну зміну.

### 10.4 Обов'язкова архітектурна перевірка кожної зміни (§42 маніфесту)

Перед створенням або зміною будь-якого програмного складника кожен із 14 агентів зобов'язаний дати відповідь на 15 питань:
1. Чи виникає нова єдина точка відмови?
2. Чи не розширюються приховані повноваження?
3. Чи залишається доступним законне відновлення?
4. Чи захищено інформацію на пристрої, під час передавання й у сховищі?
5. Чи не розкриваються непотрібні метадані?
6. Чи можна відкликати створені дозволи?
7. Чи не порушується сумісність між вузлами?
8. Чи зберігається можливість ізолювати несправний складник?
9. Чи не погіршується захист людини?
10. Чи залишається зміна перевірюваною?
11. Чи є спосіб безпечного повернення?
12. Чи не збільшується залежність від початкового автора?
13. Чи не витрачаються ресурси користувачів без їхньої згоди?
14. Чи не порушуються права власників даних?
15. Чи не створюється нова небезпека для всієї мережі через один з'єднувач?

Якщо зміна порушує основні гарантії — її необхідно переглянути до впровадження.

### 10.5 Заборонені спрощення (§43 маніфесту)

Категорично заборонено: (1) називати систему абсолютно невразливою; (2) вважати кілька копій на одному сервері незалежними вузлами; (3) плутати поділ секретів із поділом файлів; (4) називати звичайне серверне шифрування повним нерозголошенням; (5) вважати пороговий підпис універсальним шифруванням; (6) довіряти вузлам лише за фактом участі; (7) автоматично надавати права випадковій більшості; (8) вважати апаратну ізоляцію абсолютним захистом; (9) автоматично відновлювати доступ без належних підтверджень; (10) приховано використовувати пристрої користувачів; (11) вимикати чинні сервери до створення незалежних альтернатив; (12) замінювати перевірені протоколи власними неперевіреними алгоритмами; (13) позначати випробування успішними без доказів; (14) встановлювати критичні оновлення без належного погодження.

### 10.6 Послідовність етапів (0–12), обов'язкові документи (25) та перші дії агентів (§36, §44, §45)

- **Послідовність етапів (§36):** Етап 0 (повний аудит) → Етап 1 (архітектурне ядро) → Етап 2 (випробувальна мережа) → Етап 3 (шифрування та зберігання) → Етап 4 (розподілені ключі) → Етап 5 (незалежна ідентичність) → Етап 6 (розподілене керування) → Етап 7 (самовідновлення) → Етап 8 (перенесення служб) → Етап 9 (захист від примусу) → Етап 10 (ширше розгортання) → Етап 11 (незалежний аудит) → Етап 12 (постійний розвиток без залежності від початкового автора).
- **Перші дії агентів (§45):** 1) аудит дійсного проєкту й живого способу встановлення → 2) цільова схема «Плющ» → 3) порівняння перевірених технологій → 4) поетапний план незалежних випусків → 5) лише потім ізольовані випробування та реалізація без зміни робочого середовища без затвердження власника. Уся документація ведеться двомовно (`uk` + `nl`, перелік 25 обов'язкових документів — у §44 маніфесту).

## 11. Єдина жива база сповіщень і кодів дій · Eén levend register van meldingen en actiecodes (`MELDINGEN-REGISTER-001` / `B-026`, з 22.11.2026)

Панель сповіщень («Пульт уваги, спокою та дії») охоплює всі розділи й піддомени «Мого простору». Безособові порожні картки без змісту й контексту (на кшталт колишньої заглушки «Дія в технічному просторі») заборонені. Кожне виконання `npm run build` запускає `node scripts/meldingen-register-controle.mjs` і зупиняє складання з помилкою, щойно в `backend/` або `server/` з'являється незареєстрований код дії або некласифікований запис `'overig'`.
