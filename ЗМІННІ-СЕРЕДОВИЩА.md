# Змінні середовища та секрети (`ENV-VARS`)

Усі значення зберігаються на ВМ у файлі **`/etc/mijn-ruimte/geheimen.env`** (`0600 root:root` достатньо: systemd читає його від імені root; або `root:mijnruimte 0640`),
який завантажується через systemd (`EnvironmentFile=` у `deploy/mijn-ruimte.service` та в планувальник розкладу-юнітах).
Ніколи в git, ніколи у складанні, ніколи в журналах. **Згенеруйте УСІ секрети заново**: старі значення з AppDeploy
слід вважати скомпрометованими (див. [НОТАТКИ-БЕЗПЕКИ.uk.md](./НОТАТКИ-БЕЗПЕКИ.uk.md) / [НОТАТКИ-БЕЗПЕКИ.md](./НОТАТКИ-БЕЗПЕКИ.md)).

Формат `geheimen.env`: одна пара `ІМ'Я=значення` на рядок, без лапок і без `export`.

**Створення та підтримка (20.10.2026):** `sudo /usr/local/sbin/mijn-ruimte-installeer geheimen` створює всі ВІДСУТНІ
ключі (наявні залишаються без змін; показуються лише назва + відбиток), а `mijn-ruimte-installeer installeren` виконує це
автоматично як перший крок. Реєстр без значень (назва, призначення, де зберігається, відбиток, дата): `mijn-ruimte-installeer
geheimen-register --uit /etc/mijn-ruimte/GEHEIMEN-REGISTER.md` (шаблон: `розгортання/РЕЄСТР-ТАЄМНИЦЬ.md`). OAuth-клієнти
Google/Microsoft: `mijn-ruimte-installeer oauth-client google|microsoft` (приховане введення) або — для Google та GitHub — поле
в `admin` → Інтеграції → **Майстер під'єднань** (сховище, ключ доступу, без перезапуску).

## Обов'язкові змінні

| Назва | Призначення | Генерація / значення |
|---|---|---|
| `DATABASE_URL` | З'єднання з Postgres (база даних `mijnruimte`, роль `mijnruimte`). PostgreSQL **16 або новішої версії** (рекомендовано 17/18; див. `deploy/ОГЛЯД-РОЗГОРТАННЯ.md`). | `postgres://mijnruimte:<пароль>@127.0.0.1:5432/mijnruimte`; пароль: `openssl rand -base64 32 \| tr -d '/+='` |
| `AUDIT_IP_PEPPER` | Таємний pepper (HMAC-SHA256) для хешування IP у `app.audit` (`ip_hash`). Мін. 32 символи. **Сервер не запускається без нього** (audit-fix 10; більше немає резервного повернення стану на `RECOVERY_CODE_PEPPER`). Зміна робить старі й нові хеші непорівнюваними (без втрати даних). | `deploy/geheimen-aanvullen.sh` або `openssl rand -base64 48 \| tr -d '\n'` |
| `OWNER_EMAIL` | Електронна адреса власника (супер-адміністратора). Замінює раніше жорстко закодовану адресу. Сервер не запускається без неї. | Google-адреса власника, малими літерами. |
| `TOTP_ENCRYPTION_KEY_V1` | Ключ AES-256-GCM для TOTP-секретів (прив'язаний до ідентифікатора користувача). Без ключа: реєстрація TOTP повертає 503. | `openssl rand -base64 32` (32 байти; base64 або 64 hex-символи) |
| `RECOVERY_CODE_PEPPER` | Таємний pepper (HMAC-SHA256) для кодів відновлення. Мін. 32 символи. Без pepper: нові коди відновлення не генеруються (503). | `openssl rand -base64 48` |
| `GOOGLE_OAUTH_GRANT_ENCRYPTION_KEY_V1` | Шифрує збережені Google-гранти та оновлення-маркери доступу. | `openssl rand -base64 32` |
| `OWNER_VAULT_ENCRYPTION_KEY_V1` | Шифрує елементи у сховищі API-платформи (`admin`/`api`). | `openssl rand -base64 32` |
| `GITHUB_KOPPELING_SLEUTEL_V1` | Шифрує збережені GitHub-маркери доступу інтеграції (OAuth-маркер доступу, маркер доступу оновлення, маркер доступу встановлення GitHub App), прив'язані до користувача + шляху. Необов'язково: без цього ключа сервер використовує `TOTP_ENCRYPTION_KEY_V1`. Власний ключ кращий: тоді ротація TOTP не зачіпає інтеграцію GitHub. | `openssl rand -base64 32` |
| `HUIS_ADAPTER_SLEUTEL_V1` | Шифрує збережені маркери доступу Home Assistant у Huis vNext (міграція 0128, `app.huis_integraties.geheim`), прив'язані до оселі + інтеграції. Необов'язково: без цього ключа сервер використовує `TOTP_ENCRYPTION_KEY_V1`. Власний ключ кращий: тоді ротація TOTP не зачіпає під'єднання шлюзів. Ротація = повторне під'єднання всіх інтеграцій (маркер доступу ніколи не повертається у відкритому вигляді). | `openssl rand -base64 32` |
| `MAIL_TOKEN_ENCRYPTION_KEY_V1` | Шифрує маркери доступу поштових постачальників. Має бути рівно 32 байти. | `openssl rand -base64 32` |
| `MAIL_APP_WACHTWOORD_SLEUTEL_V1` | **Обов'язковий з 20.10.2026.** Шифрує пароль додатка IMAP/SMTP-під'єднань (iCloud, Ukr.net, Yahoo, I.ua; `backend/mail-imap.ts`), прив'язаний до користувача + рядка + простору. Без ключа під'єднання відхиляється з кодом помилки (ніколи не зберігається незашифрованим). Жодного резервного повернення стану на інший ключ. | `mijn-ruimte-installeer geheimen` або `openssl rand -base64 32` |
| `AGENDA_ABONNEMENT_SLEUTEL_V1` | Шифрує пароль додатка CalDAV-календаря (iCloud, Fastmail, Nextcloud), прив'язаний до користувача + адреси сервера. Потрібен лише якщо хтось під'єднує CalDAV; без ключа сайт відхиляє під'єднання з `CALDAV_SLEUTEL_ONTBREEKT` замість збереження пароля незашифрованим. Для ICS-підписок і Google Calendar він не потрібен. | `openssl rand -base64 32` |
| `SLEUTELKLUIS_SLEUTEL_V1` | **Обов'язковий з 21.10.2026** — створюється через `mijn-ruimte-installeer` перед міграцією 0092 (сховище ключів / sleutelkluis). Не видаляти і не ротувати. Pepper для конвертів ШІ-під'єднань: ключ даних (DEK) людини обгортається для MCP-під'єднання через `HKDF(маркер доступу агента + цей pepper)`. Сам DEK НІКОЛИ не лежить на диску; цей pepper нічого не відкриває без маркера доступу агента. Якщо він відсутній, сховище використовує `TOTP_ENCRYPTION_KEY_V1`; якщо відсутні обидва, ШІ-під'єднання не отримують конверта (агенти бачать «ключ закритий» на зашифрованих рядках). | `openssl rand -base64 32` |

> Якщо ви зміните будь-який `*_KEY_V1` пізніше, наявні зашифровані дані більше не можна буде прочитати.
> Тому зберігайте ключі також в поза мережею-резервній копії (менеджер паролів), окремо від резервної копії бази даних.

### Необов'язкові окремі ключі з резервним поверненням стану на `TOTP_ENCRYPTION_KEY_V1`

| Назва | Призначення |
|---|---|
| `GITHUB_KOPPELING_SLEUTEL_V1` | Маркери доступу інтеграції GitHub (див. вище). |
| `AGENT_SLEUTEL_V1` | Маркери доступу ШІ-агентів (`backend/connectors-crypto.ts`). |
| `AI_ARCHIEF_SLEUTEL_V1` | Архів оглядачевої діагностики (`backend/browser-diag-archief.ts`). |

Якщо такий ключ відсутній, код використовує `TOTP_ENCRYPTION_KEY_V1`. **Тому `mijn-ruimte-installeer geheimen` на
наявній встановленнї НЕ створює їх автоматично** (під TOTP-ключем уже можуть зберігатися дані; новий окремий ключ
зробив би їх нечитабельними). На новому порожньому `geheimen.env` вони створюються; пізніше свідомо: `… geheimen --ook-optioneel`.

### Ролі бази даних (безпека, фаза 2, необов'язково)
Записуються виключно сценарієм `deploy/db-rollen-instellen.sh instellen` (вручну ніколи не потрібно). Якщо змінна
відсутня, застосунок повертається до `DATABASE_URL` і все працює як раніше (одна роль, RLS-політики пропускають усе).

**Audit-fix 4: два файли.** Після `db-rollen-instellen.sh env-splitsen` міграційний та застарілий спадок-URL
(`DATABASE_URL`, `DATABASE_URL_MIGRATIE`) залишаються лише у **`/etc/mijn-ruimte/migratie.env`** (`0600 root:root`). Цей
файл завантажується лише кроком міграції `installeer-app.sh` та сценарієм `db-rollen-instellen.sh`, і ніколи сервісами
`mijn-ruimte.service`/`-cron`/`-backup`. У `geheimen.env` залишаються `DATABASE_URL_APP` та `DATABASE_URL_SYSTEM`. Застосунок
попереджає під час запуску, якщо міграційний або застарілий спадок-URL все ж таки наявний у середовище виконання-середовищі. Повернення назад: `env-samenvoegen`.
`migratie.env` входить до зашифрованої резервної копії секретів (див. `deploy/ВІДНОВЛЕННЯ.md`).

| Назва | Роль | Ким використовується |
|---|---|---|
| `DATABASE_URL_MIGRATIE` | `mijnruimte_migrator` (власник схеми `app`) | `dist-server/migrate.mjs` (`installeer-app.sh`) |
| `DATABASE_URL_APP` | `mijnruimte_app` (`NOBYPASSRLS`, лише DML на `app.records`) | запити авторизованих користувачів (`SET LOCAL app.user_id`) |
| `DATABASE_URL_SYSTEM` | `mijnruimte_system` (`BYPASSRLS`) | планувальник розкладу, вебвиклики, вхід/сеансу, маршрути адміністрування, `backup-maken.sh` |

Примусове застосування RLS зберігається в базі даних (`app.rls_instellingen.afdwingen`), а не у змінній середовища: застосунок не може
вимкнути його самостійно. Перемикання: `db-rollen-instellen.sh rls-aan|rls-uit`.

### Безпека, фаза 2/3: перемикачі (необов'язково)

| Назва | Типово | Призначення |
|---|---|---|
| `AUTH_POORT_AFDWINGEN` | вимк. | `1` = запобіжник у маршрутизаторі відповідає **401** на кожну анонімну 2xx-відповідь маршруту, якого немає в `PUBLIEKE_ROUTES` (`server/platform/auth-poort.ts`). Без цього: лише журналювання (`[auth-poort]`) і підрахунок у `app.rls_audit` (дія `anoniem-2xx`). Див. `deploy/ІНСТРУКЦІЯ-ЕТАПІВ-2-3.md`. |
| `STAP_OP_UIT` | вимк. | Аварійний вимикач: `1` вимикає вимогу додаткове підтвердження (`STEP_UP_REQUIRED`) для чутливих дій. Використовувати лише тимчасово, напр., якщо клієнтська частина ще не обробляє додаткове підтвердження, а адміністративна дія є терміновою. |
| `STAP_OP_GOOGLE_ZONDER_AUTH_TIME` | вимк. | Opt-in резервний шлях (audit-fix 5): `1` = явний додаткове підтвердження вхід через Google (`prompt=login`, `max_age=0`) зараховується навіть без поля `auth_time` в `id_token`, за умови що OAuth-потік завершено протягом 5 хвилин після старту. Типово Google-додаткове підтвердження зараховується лише з `auth_time` (увімкніть у Google Cloud Console для OAuth-клієнта **"сеанс age claims"**). TOTP-додаткове підтвердження працює завжди. |
| `ACCOUNT_DEFINITIEF_WISSEN` | вимк. | `1` = фонова задача очищення видаляє облікові записи **остаточно** (вміст, ідентичності, файли; залишається лише запис-надгробок без персональних даних), щойно минає 30-денний період відновлення. Без цього: лише сухий звіт у журналах планувальник розкладу. **Необоротно** — вмикати лише після успішного тесту резервного копіювання та відновлення. |

## Вхід через Google та Google Suite (необов'язково: без цих значень Google-вхід вимкнено)

| Назва | Призначення | Генерація / значення |
|---|---|---|
| `GOOGLE_OAUTH_CLIENT_ID` (аліас `GOOGLE_SUITE_CLIENT_ID`; якщо заданий і він, перемагає `GOOGLE_SUITE_CLIENT_ID` — це має бути той самий клієнт) | OAuth Client ID (публічний). | Google Cloud Console → *APIs & Services* → *Credentials* → *Створити облікові дані* → *OAuth client ID*, тип *Web application*. Redirect URI: **`https://id.<ваш-домен>/`** (точно, зі слешем у кінці); JavaScript origins: `https://id.`, `https://hub.`, `https://mail.`, `https://cloud.<ваш-домен>`. Обсяги повноважень та брендинг у *Google Auth Platform* (раніше «OAuth згода screen»). **Майстер під'єднань** показує ці значення готовими до копіювання для вашого домену. |
| `GOOGLE_OAUTH_CLIENT_SECRET` (аліас `GOOGLE_SUITE_CLIENT_SECRET`) | OAuth Client Secret. | З того самого клієнта. Встановлення: `mijn-ruimte-installeer oauth-client google` (приховане введення, перезапуск + перевірка). **Або** через майстер у сховищі (призначення `google`, назва `google-oauth-client`, рядки `client_id:`/`client_secret:`): env має пріоритет; якщо в env НЕМАЄ клієнта, діє сховище власника — без перезапуску (вхід через Google протягом 5 хв; Gmail/Drive/Agenda миттєво). Ніколи наполовину: лише id або лише секрет в env не доповнюється зі сховища. |

Без клієнта (ні в env, ні у сховищі) вхід через Google відповідає **503 `GOOGLE_NOT_CONFIGURED`** (і не створює рядків стану).
Майстер перевіряє клієнта без входу: запит до token кінцева точка із тестовим кодом → `invalid_grant` = дійсний, `invalid_client` = недійсний.

**Фото відправників із Google-контактів (необов'язково, 21.10.2026):** увімкніть у тому самому проєкті Google Cloud також **People API**.
Сайт запитує `contacts.readonly` та `contacts.other.readonly` лише тоді, коли людина в Пошта → Налаштування → «Відправники» сама
вмикає «Фото відправників з ваших Google-контактів» (інкрементальна згода на наявному під'єднанні Gmail; звичайне під'єднання
їх не запитує). Якщо API вимкнено, сторінка чесно повідомляє про це, а все інше продовжує працювати.

## Швидка генерація всього (на ВМ, від імені root)

Якщо `geheimen.env` уже існує (з `DATABASE_URL`), використовуйте `mijn-ruimte-installeer geheimen --eigenaar <e-mail>`
(`deploy/geheimen-aanmaken.sh`; стара назва `geheimen-aanvullen.sh` вказує на нього): це додає лише відсутні ключі,
не показує значень у терміналі й записує назву + відбиток у `geheimen.journaal`. Для повністю нового файлу це можна зробити
й вручну:

```bash
install -d -m 0750 -o root -g mijnruimte /etc/mijn-ruimte
umask 027
cat > /etc/mijn-ruimte/geheimen.env <<EOT
DATABASE_URL=postgres://mijnruimte:$(openssl rand -base64 32 | tr -d '/+=')@127.0.0.1:5432/mijnruimte
OWNER_EMAIL=<eigenaar@gmail.com>
TOTP_ENCRYPTION_KEY_V1=$(openssl rand -base64 32)
RECOVERY_CODE_PEPPER=$(openssl rand -base64 48 | tr -d '\n')
AUDIT_IP_PEPPER=$(openssl rand -base64 48 | tr -d '\n')
GOOGLE_OAUTH_GRANT_ENCRYPTION_KEY_V1=$(openssl rand -base64 32)
OWNER_VAULT_ENCRYPTION_KEY_V1=$(openssl rand -base64 32)
GITHUB_KOPPELING_SLEUTEL_V1=$(openssl rand -base64 32)
MAIL_TOKEN_ENCRYPTION_KEY_V1=$(openssl rand -base64 32)
MAIL_APP_WACHTWOORD_SLEUTEL_V1=$(openssl rand -base64 32)
AGENDA_ABONNEMENT_SLEUTEL_V1=$(openssl rand -base64 32)
GOOGLE_OAUTH_CLIENT_ID=
GOOGLE_OAUTH_CLIENT_SECRET=
EOT
chown root:mijnruimte /etc/mijn-ruimte/geheimen.env && chmod 0640 /etc/mijn-ruimte/geheimen.env
```
(Пароль бази даних після цього також потрібно встановити через `ALTER ROLE mijnruimte PASSWORD '…'`.)

## Необов'язкові змінні (не секрети)
- `CHAT_MODEL` — модель для чату на `ai.*` (типово `claude-sonnet-5-5`). Сам ключ Anthropic НЕ зберігається в середовищі:
  кожен користувач зберігає власний ключ у сховищі власника (`purpose: anthropic`, API → Koppelingen → Kluis).
- `EXTERNE_MCP_HOSTS` — білий список хостів, куди сайт може звертатися як **MCP-клієнт** (коли сайт сам спілкується зі
  стороннім MCP-сервером; `backend/mcp-klant/*`, міграція 0078). Розділені комами або пробілами; кожен запис — це ім'я хоста
  (`api.githubcopilot.com`) або суфікс з однією зірочкою попереду (`*.githubcopilot.com`). Окрема `*` ігнорується.
  **Якщо нічого не задано: жодних вихідних MCP-з'єднань** — так і задумано (BYOS: лише туди, куди власник свідомо дозволив).
  Той самий список може також міститися у root-файлі, який уже використовують двері MCP,
  `/etc/mijn-ruimte/mcp-rechten.json` (шлях налаштовується через `MCP_RECHTEN_PAD`), під ключем `externeMcpHosts`:
  `{ "externeMcpHosts": ["api.githubcopilot.com"] }`. Якщо задані обидва, діє їхнє об'єднання. Маркери доступу тут НЕ зберігаються: їх
  користувач сам кладе у своє сховище під час під'єднання (`mcp.*` → Під'єднання ШІ → «Зовнішні MCP»).
  З 22.10.2026 власник керує `externeMcpHosts` безпосередньо на тій сторінці за допомогою **ключ доступу-рішення** (root записує файл;
  ІНСТРУКЦІЯ-БЕЗПЕЧНОГО-РОЗГОРТАННЯ §15); хости з `EXTERNE_MCP_HOSTS` відображаються там як «середовище» і змінюються лише тут.
- `BESLUIT_INBOX` (типово `/srv/mijn-ruimte/besluit-inbox`), `BESLUIT_APP_ROOT` (типово `/srv/mijn-ruimte`: `current`, `VORIGE`,
  `releases/`) — рішення власника з ключ доступу (`backend/eigenaar-besluit.ts`, ІНСТРУКЦІЯ-БЕЗПЕЧНОГО-РОЗГОРТАННЯ §15): куди застосунок кладе підписане
  рішення для root і звідки читає активний/попередній випуск. Результат надходить із `OPDRACHT_STATUS_DIR/besluit-<id>.json`.
  Використовується лише для тестів і перевірки стану; на сервері діють фіксовані шляхи. Сам root-сценарій (`mijn-ruimte-besluit`) читає `BESLUIT_*`
  (`BESLUIT_WERK`, `BESLUIT_STATUS`, `BESLUIT_RECHTEN`, `BESLUIT_PASSKEY`, `BESLUIT_INSTALLEER`, `BESLUIT_GROEP`, `BESLUIT_WACHT_TERUG`)
  виключно поза root і лише зі шляхами всередині `/tmp`.
