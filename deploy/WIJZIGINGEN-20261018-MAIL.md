## Перевірені відправники / Geverifieerde afzenders (виконавець M2, гілка артефакту f252547a, міграція 0064)
- **Власна база даних на кожен акаунт** (`app.mail_afzenders`, RLS «власні рядки»; прогрес першої перевірки в `app.mail_afzender_audit`, запис лише системною роллю). Для кожної адреси: статус `geverifieerd | onbekend | verdacht`, джерело (`handmatig | bekende-dienst`; `authenticatie` зарезервовано, ніколи не ставиться автоматично), код причини, доказ (останній SPF/DKIM/DMARC + лічильники), вперше/востаннє бачено, кількість, нотатка, історія (останні 50).
- **Правила** (`shared/mail-afzenders.ts`, чисті функції): «geverifieerd» (перевірено) ставиться лише (a) вручну користувачем або (b) якщо домен входить до курованого списку `shared/mail-bekende-afzenders.ts` (із джерелом для кожного бренду; безкоштовні поштові сервіси — ніколи) **ТА** верхній заголовок `Authentication-Results` від `mx.google.com` містить `dmarc=pass` для цього From-домену або `dkim=pass` від того самого організаційного домену. Підроблені/нижчі рядки AR не враховуються. «Verdacht» (підозрілий): назва бренду як відображуване ім'я при іншому домені, інша адреса у відображуваному імені, схожий домен (`paypa1`, `paypal-security`, `paypal.com.evil.ru`, кириличні омогліфи, зокрема в punycode), ім'я підтвердженого контакту з іншою адресою або `dmarc=fail` для домену бренду. Підтвердження вручну ніколи не скасовується автоматично; підроблений лист із такої адреси позначається червоним і рахується окремо для конкретного листа.
- **API** `POST /api/owner/mail/afzenders/{status,controle,lijst,detail,verifieren,intrekken,bijwerken,vervangen,verwijderen,audit/start,audit/status,audit/stop}` (поштова сесія, схвалений користувач). Лінива перевірка: для відправників із відомого домену бренду без підтвердження сервер читає для ≤ 5 листів за запит (≤ 40 за 5 хв) лише `From/Date/Authentication-Results` (`format=metadata`). Журнал `owner.mail.afzender.*` містить лише домен + короткий геш адреси.
- **Перша перевірка**: кнопка «Провести аудит відправників» у Налаштування → Безпека → Відправники. Сторінки по 50, 5 одночасно, пауза між сторінками, одна транзакція на сторінку (нічого не рахується двічі), можливість продовження після помилки/зупинки/перезапуску (токен сторінки), при ліміті Gmail — повторна спроба, а потім «помилка» з кодом.
- **Інтерфейс**: пігулка поруч із ім'ям у всіх режимах щільності (normal/detailed/bulky через `MailMessageRow`, minimum через `MailMinimumMessageRow`) і в шапці відкритого листа (`MailThreadContent`): прапорець (зелена, підказка «як перевірено»), помаранчева (ім'я + адреса видимі, наведення/фокус → пояснення + «Перевірити вручну і зберегти в контакти»), червона «Можливе видавання себе за інший сервіс» (у переглядачі з текстовою міткою). Вікно з адресою, доменом, SPF/DKIM/DMARC саме ЦЬОГО листа, ім'ям, нотаткою, обов'язковим підтвердженням (+ друге при підозрілому). Керування: пошук, фільтр за статусом із лічильниками, підтвердження/відкликання/редагування/заміна адреси/видалення, історія, пагінація. Ніколи не передається лише кольором (іконка + текст для скрінрідерів); кліки/клавіші на пігулці чи у вікні не відкривають сам лист.
- **Тести**: `mail-afzenders` 60/60 (62/62 з роллю застосунку через `run-test-rls.sh`: B бачить 0 рядків без ДЕ і не може записати рядок для A); браузерний стенд `/tmp/h-M2/test.py` 104/104 (uk/nl, світла/темна тема, 1280/390; зі справжнім CSS рядків). Наявні поштові тести зелені (`mail-*` включно з `mail-qa-2026-10-12`, `mail-rij-2026-10-18`, `mail-uittreksel`), `routes` 5/5, `beheer-journaal` 44/44.
- **Не доведено**: справжні заголовки Gmail на живому сервері (у тестах джерело Gmail підмінено), повнота курованого списку доменів проти всіх реальних відправників користувача (відсутні регіональні домени → підтверджувати вручну).

## Дзвоник сповіщень провалювався під екран із технічною смугою (повідомлення власника від 18.10.2026, зі знімком екрана)
- **Причина:** при активному технічному профілі `#root` отримує `transform` + `top: var(--tech-band-h)` (`src/tech/tech.css`). Через це `#root` стає containing block для фіксованого дзвоника, але дзвоник рахував координати у пікселях вікна (`visualViewport`): `top` = вікно − 58 px опинявся на 40/44 px нижче, ніж треба → наполовину або повністю за нижнім краєм. Щойно смуга ховалася (`#root{top:0}`), усе ставало на місце — точнісінько як у повідомленні.
- **Рішення:** новий `src/platform/vast-kader.ts` — `zichtbaarKader()` повертає видиму область у координатах containing block (+ зміщення `kx/ky`), `volgKader()` перераховує при вмиканні/вимиканні/приховуванні смуги (`data-tech`, `data-tech-verborgen`, стиль `#root`, кінець анімації). `CanonicalNotificationCenter.tsx`: розташування, перетягування (`clientX/Y − kx/ky`), панель і спливне сповіщення поруч із дзвоником — у координатах рамки. `MailComposeFloat.tsx`: «Написати лист» також слідує за дзвоником при вмиканні/вимиканні смуги.
- **Тести:** `vast-kader` 20/20 (відтворює стару поведінку: 30/34 px нижче екрана). Браузер (Chromium, справжній компонент із `tech.css`, 1280×900 і 390×844): 12/12 — дзвоник повністю видимий зі смугою та без неї, після приховування й повернення смуги, перетягування під курсором, панель у межах екрана. Той самий тест на старому компоненті: 3 ПОМИЛКИ (нижній край дзвоника 930 px при висоті вікна 900 px) → тест ловить заявлену помилку.

## Повідомлення власника від 18.10.2026 (після встановлення 20261018-151122): сторінка стрибає вгору + збій резервної копії
