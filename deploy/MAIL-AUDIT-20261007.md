# Аудит поштового клієнта mail.tarasevych.com (07.10.2026)

Метод: читання коду (`backend/google-suite-mail-browser.ts`, `backend/index.ts`, `src/MailNewMessageDialog.tsx`, `src/MailComposeEditor.tsx`), запити до живої бази (лише лічильники й
стани, без вмісту листів), живі запити від імені власника до маршрутів на проді, журнали cron. Інтеграція з Gmail: **офіційний REST API через fetch** (бібліотека `googleapis`
не потрібна й не додавалась); IMAP/SMTP не використовується.

## Що працює
- Читання: список, потоки, мітки, пошук, період-межі, вкладення (`google-suite/*`, токен principal).
- Архівування: `message/modify` для дії `archive` викликає `POST /gmail/v1/users/me/messages/{id}/modify` з `{"addLabelIds":[],"removeLabelIds":["INBOX"]}` (перевірено в коді; для кошика окремі `trash/untrash`). **Виправляти не довелось.**
- Відкладання листа «snooze» (`mail-snooze.ts`) існує як окрема функція.
- Cron: `mail-provider-maintenance` (5 хв) і `google-suite-bplus-sync` (5 хв) відпрацьовують без помилок.

## Що ламалось (знайдено й виправлено)
1. **Синхронізація пошти стояла з 4.10.2026 15:20** (три дні). Причина: цикл виконання завдань (`mailRunDueJobs`) читав лише **перші 100** завдань власника у порядку створення; ці
   100 були всі `succeeded`, а 293 нових `queued` стояли далі й ніколи не потрапляли в вибірку (те саме в `mailRecoverStaleJobs`, ліміт 300). Cron при цьому звітував «ok 200».
   Виправлення: вибірка за статусом (`queued`/`retry`/`leased`), очищення завершених (>3 доби) і застарілих резервних синхронізацій (`mailPurgeJobs`), тест `mail-queue` (4 перевірки).
   Після розгортання: 389 завдань очищено, 3 виконано за один запуск, початкова синхронізація знову йде.
2. **Cron не показував помилки**: `cron.ts` вважав усе зі `statusCode 200` успіхом, тоді як тіло могло містити `ok:false` чи причину по власнику. Тепер `app.cron_runs.detail` містить стан
   і скорочене тіло, а `ok:false` позначається як `error`.
3. **Кнопка «Написати лист» не могла надіслати лист**: вікно слало на `/api/owner/mail/accounts/<id>/send/prepare` ідентифікатор облікового запису **Google-suite** (`1a4a…`), а маршрут шукає обліковий запис
   старої «mail platform» (`d497…`) → `404 MAIL_ACCOUNT_NOT_FOUND`. Навіть із правильним id відповідь `503 MAIL_GMAIL_RUNTIME_DISABLED` (рантайм Gmail старої платформи вимкнений). Перевірено живими запитами.
   До того ж надсилався лише звичайний текст без форматування. Тепер надсилання йде новим маршрутом `compose/send` (Gmail API `messages/send`, HTML + текст, ідемпотентне).
4. **Чернеток на сервері не було**: лише `localStorage` браузера (затримка 400 мс; зникає при очищенні даних і не видно на іншому пристрої), синхронізації з Gmail нема. Тепер: затримка 700 мс →
   PostgreSQL (`app.mail_drafts`) → Gmail `drafts.create/update`, стан у вікні (збережено / лише на сервері / лише в браузері), відновлення із сервера, видалення чернетки після надсилання.
5. **Відкладеного надсилання не було** (лише snooze). Тепер: таблиця `app.mail_queue` (міграція 0016), маршрути `compose/schedule|scheduled/list|cancel`, cron `mail-queue-send` щохвилини
   (`mijn-ruimte-mail-queue.timer`), `FOR UPDATE SKIP LOCKED` (двічі не надсилається), повтори з паузою до 5 спроб, постійна помилка → `failed`, «завис у sending >10 хв» → `failed (невідомо)` без повторної
   надсилання (щоб не було дубля). Зберігання «у пам'яті» не додавав: джерело істини БД, cron щохвилини; пам'ять дала б ризик дублів.
6. **Вбудований `ai` вимкнений** (`AI_NOT_CONFIGURED`), тому наявний переклад у читанні завжди повертає 503. ШІ-помічник тепер працює через **власний ключ Anthropic користувача** (сховище, призначення `anthropic`).

## Що ще не працює або не перевірено
- **Push (Pub/Sub)**: код є, але в секретах нема `GOOGLE_GMAIL_PUBSUB_TOPIC/AUDIENCE/SERVICE_ACCOUNT_EMAIL`; для нового типу облікового запису (grant) push свідомо був вимкнений (`bplus_history_fallback`).
  Тепер увімкнеться сам після налаштування; інструкція `deploy/MAIL-PUSH-PUBSUB.md`. Справжній push від Google **не перевірено** (потрібні дії у Google Cloud).
- Обліковий запис у старій платформі лишається в стані `initial_sync` / `bplus_grant_waiting_initial_sync` (потрібно кілька циклів cron, щоб завершити початкову синхронізацію; слід перевірити, що стан став `connected`).
- Реальне надсилання листа з прода я **не** запускав (це дія від вашого імені). Протестовано: MIME, чернетки, черга, повтори, паралельні воркери (25 перевірок із підробленим Gmail), ШІ-помічник (18 перевірок).
- ШІ-кнопки у вікні нового листа працюють лише з вашим ключем Anthropic; без ключа показується підказка. Підсумок потоку, відповідь за контекстом і оцінка тону є на сервері
  (`compose/ai/summarize|reply|tone`), але кнопок у вікні читання листа ще нема (читання — окремий великий мінімізований компонент; потрібен окремий етап).
- 173 помилки типів у фронтенді (поштові перегляди) лишаються.
- Ліміти вибірок (`limit:`) у інших місцях `index.ts` теж обмежують «перші N» записів; варто перевірити решту викликів `db.list` для великих таблиць.
