# Нотатки до випуску — Технічні простори v2

**BRON-COMMIT:** див. файл `BRON-COMMIT` в архіві (master, /workspace/werkblad-v3). **Не розгорнуто.** Прод не
чіпали; жодного запиту до *.tarasevych.com (усі тести запускалися локально, Chrome з прив'язкою хостів до 127.0.0.1, 0 зовнішніх запитів).

## Підсумок
Два паралельні простори одного облікового запису: «Звичайний простір» і «Технічний простір». Перемикання без повторного входу
(повернення у Звичайний = **пауза**), три чіткі терміни: «На час (до HH:MM)», «До завершення технічного сеансу»,
«До виходу з облікового запису на сайті». Вихід із сайту завжди закриває й технічний сеанс; «Вийти з технічного сеансу» ніколи не виходить
із сайту; вихід в одній вкладці залишає довгі розблокування розширення («1 рік», «без обмеження») чинними — лише вихід з облікового запису на сайті або
«Вийти всюди» відкликає їх. Єдина функція ухвалення рішень (`shared/ruimte-toegang.ts`) для сайту, ШІ/MCP та розширення; доступ ШІ використовує ті самі
три терміни. Недоступні терміни залишаються видимими, неактивними (сірими), із зазначенням причини. Нове вікно «Доступ і терміни» (6 вкладок),
три варіанти виходу з поясненням наслідків. Контракт: `docs/ontwerp/TECH-RUIMTES-API.md`. Інструкції (runbooks): `deploy/RUNBOOK-VEILIGE-UITROL.md` §17 та
`deploy/RUNBOOK-TECH-RUIMTES-UI.md`.

## Прапорець — типово ВИМКНЕНО
- `tech-ruimtes-v2` (типово **вимкнено**): вимкнено = точно стара поведінка (старе меню «Технічний профіль · …», старе вікно активації).
- `tech-ruimtes-v2-schaduw` (вимкнено) або змінна середовища `TECH_RUIMTES_V2_SCHADUW=1`: **тіньовий режим (schaduwmodus)** — поведінка залишається старою, розбіжності з новим
  правилом записуються в журнал як `owner.tech.schaduw.verschil` (див. §17.2).

## Міграція
`npm run migrate` виконує `0115_tech_ruimtes_v2` (ідемпотентно). Перевірка:
`SELECT sleutel, aan FROM app.feature_flags WHERE sleutel LIKE 'tech-ruimtes-v2%';` → два рядки, обидва `false`.

## Увімкнення (спершу лише для власника)
1. Розгорнути + `npm run migrate`. Нічого не змінюється.
2. (Рекомендовано) кілька днів у тіньовому режимі (§17.2).
3. На сайті: меню облікового запису → «Технічний профіль» → увімкнути старий технічний профіль (з підтвердженням) → вікно «Прапорці» →
   `tech-ruimtes-v2` → «Тест: так» (лише для вас, до 03:00 / до завершення технічного профілю), **або** «Змінити» → головний перемикач увімкнути лише з
   вашим обліковим записом у списку. Альтернатива в SQL:
   `UPDATE app.feature_flags SET aan = true, gebruikers = ARRAY['<user-id власника>'] WHERE sleutel = 'tech-ruimtes-v2';`
4. Перезавантажити сторінку (Ctrl+F5). Меню облікового запису тепер показує перемикач «Звичайний простір | Технічний простір» та «Доступ і терміни».
   Поточні СТАРІ активації більше не враховуються: запустіть технічний простір заново через перемикач (попросить підтвердження).

## Повернення стану
`UPDATE app.feature_flags SET aan = false, gebruikers = '{}' WHERE sleutel = 'tech-ruimtes-v2';` (або вимкнути «Тест») → за 3 с повертається стара
поведінка. Таблиці `app.tech_ruimte_*` залишаються і не читаються. Повернути попередній архів за інструкцією також можливо
(міграцію 0115 повертати попередній стан не потрібно).

  Тепер: використовується служба сесії поточного хоста; помилка більше не запам'ятовується.
- **Помилка 2 (виправлено):** натискання на «Технічний простір» до того, як технічний шар (TechLaag, завантажується після застосунку) був готовий, губився
  (нічого не відбувалося). Тепер запит зберігається на 10 с і підхоплюється під час завантаження — лише коли прапорець увімкнено.
- Новий справжній E2E: `scripts/lokaal-e2e/tech-ruimtes-v2-integratie.mjs` (справжній бекенд + PostgreSQL, справжнє підтвердження TOTP у вікні).

## Що НЕ перевірено
- Вхід через Google та підтвердження через passkey/Google (локально неможливо): сесію сайту посіяно в БД; підтвердження проходило
  через справжній TOTP-код у справжньому вікні (автентифікатор посіяно в БД).
- Вихід в одній вкладці викликано тим самим API-запитом, що й клієнт (`logout-current`), через fetch на сторінці; саме меню хаба
  має лише «Вийти з цього обліковому запису» (увесь браузер).
- Сама дія «Вийти всюди» (кнопка з підтвердженням на сторінці Безпека → Сесії) не натискалася; перевірено лише перенаправлення.
- Справжнє розширення браузера і справжній MCP-клієнт: розблокування та MCP-з'єднання посіяно в БД; поведінка MCP-шлюзу перевірена лише в
  модульному тесті (58).
- Тіньовий режим лише в модульному тесті; адмінсторінки з примусовим режимом (`beheer-alleen-tech`) у браузері не тестувалися.
- Інші піддомени, крім hub.* (mail, id, …), не перевірялися у справжньому E2E; темна тема лише з фейковим сервером.
- Жодних тестів проти проду чи продуктової бази даних.
