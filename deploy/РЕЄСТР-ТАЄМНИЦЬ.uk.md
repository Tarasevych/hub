# Реєстр секретів «Mijn Ruimte» — ШАБЛОН

> **Тут немає жодного значення — і не має бути.** Значення живуть лише на вашому сервері (`/etc/mijn-ruimte/geheimen.env`,
> зашифроване сховище в базі) і в вашому менеджері паролів. Цей файл — карта: що є, для чого, де лежить, який у нього
> відбиток і коли його створили. Відбиток (SHA-256 значення, перші 8 hex) дозволяє звірити «той самий ключ чи ні», не
> показуючи ключ.

## Як отримати актуальний реєстр

На сервері, від робочого користувача (напр. `beheer`), один раз після кожної зміни секретів:

```bash
sudo /usr/local/sbin/mijn-ruimte-installeer geheimen-register --uit /etc/mijn-ruimte/РЕЄСТР-ТАЄМНИЦЬ.md
sudo cat /etc/mijn-ruimte/РЕЄСТР-ТАЄМНИЦЬ.md      # перегляд; файл root 0600
```

Без `--uit` реєстр друкується в термінал. Сценарій: `deploy/geheimen-register.sh`. Дати беруться з `geheimen.journaal`
(який ведуть `mijn-ruimte-installeer geheimen` і `… oauth-client`); для старіших записів — дата файлу `geheimen.env` з
позначкою «(bestand)».

Відсутні ключі створити (наявні не змінюються): `sudo /usr/local/sbin/mijn-ruimte-installeer geheimen`.
Цей самий крок виконується автоматично на початку кожного `mijn-ruimte-installeer installeren`.

### Ротація ключа конвертів (SEC-002, geheimen-07)

Ключі, якими сервер запечатує конверти через `sealWithEnvKey` (`TOTP_ENCRYPTION_KEY_V1`, `MAIL_APP_WACHTWOORD_SLEUTEL_V1`,
`AGENDA_ABONNEMENT_SLEUTEL_V1`, `GITHUB_KOPPELING_SLEUTEL_V1`, `AGENT_SLEUTEL_V1`, `AI_ARCHIEF_SLEUTEL_V1`, `HUIS_ADAPTER_SLEUTEL_V1`),
мають версію в конверті (`v1.…`, `v2.…`). Після підозри на витік або за графіком:

1. Додайте новий ключ `<НАЗВА>_V2` (32 випадкові байти, `openssl rand -base64 32`) у `geheimen.env` і перезапустіть службу.
2. Відтоді сервер записує кожен НОВИЙ або змінений конверт під V2 (`v2.…`); наявні конверти `v1.…` і далі читаються ключем V1.
3. **V1 ніколи не прибирати** (навіть якщо рядків `v1.…` начебто вже немає): наявні конверти `v1.…` читаються лише ключем V1.
   Модулі з резервним ключем TOTP (`AGENT_SLEUTEL_V1`, `GITHUB_KOPPELING_SLEUTEL_V1`, `AI_ARCHIEF_SLEUTEL_V1`, `HUIS_ADAPTER_SLEUTEL_V1`)
   бачать власний ключ у будь-якій версії (`envSleutelBeschikbaar`), тож установка з `_V2` мовчки на TOTP не переходить.
   Ротація тут означає: нові дані — під V2, витеклий V1 читає лише старі рядки. Перезапечатування всіх рядків `v1`, лічильник на
   сторінці «Секрети й ключі» і заміна ключа даних (DEK) ще не зроблені (звіт SEC-002, geheimen-07).
4. База даних: лише з міграції 0253 обмеження CHECK приймають `v1.` … `v9.` (IMAP, CalDAV, підтвердження ШІ). До 0253 не ротувати.

Не цим шляхом: `GOOGLE_OAUTH_GRANT_ENCRYPTION_KEY_V1`, `OWNER_VAULT_ENCRYPTION_KEY_V1`, `MAIL_TOKEN_ENCRYPTION_KEY_V1`
(власний формат конверта) і перці (`RECOVERY_CODE_PEPPER`, `AUDIT_IP_PEPPER`, `SLEUTELKLUIS_SLEUTEL_V1`): для них і далі «не ротувати».
Покроково з наслідками — також у `ЗМІННІ-СЕРЕДОВИЩА.uk.md`, розділ «Ротація ключів конвертів».

### Сховище секретів власника (не env)

Записи сховища — GitHub OAuth-застосунок (`github-oauth`), GitHub App (`github-app`), Google-клієнт (`google`), Telegram,
Anthropic, Home Assistant… — мають власний перелік **Адміністрування → «Секрети й ключі»** (назви, дати, терміни, без
значень). Їх вводять лише через сайт із ключ доступу/TOTP; у цьому файлі їх не дублюють.

### Де зберігати цей файл

- Поруч із самими значеннями у менеджері паролів власника (окремий запис «Mijn Ruimte — реєстр»).
- У зашифрованій резервній копії секретів (`deploy/ВІДНОВЛЕННЯ.md`), окремо від копії бази.
- **Не** в git, **не** в чаті, **не** в тикетах.

### Правило

Жоден секрет не проходить через чат, файли від ШІ чи інструкції: він генерується на сервері (`openssl rand`) або в консолі
постачальника й одразу лягає на сервер (прихований ввід). ШІ-помічник бачить лише назви й відбитки.
