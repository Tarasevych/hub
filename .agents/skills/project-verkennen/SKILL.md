# Ознайомлення з проєктом Mijn Ruimte

## Призначення

Використовуй навичку, якщо треба з'ясувати, як побудовано сайт, де розташовано службу, які взаємозв'язки між складниками, чому певна можливість існує або який порядок роботи застосувати.

## Порядок

1. Прочитай `AGENTS.md`, `orchestratie/beleid.json`, чинні рішення в `orchestratie/BESLUITEN.md` та — для будь-якого архітектурного чи інфраструктурного питання — Головний архітектурний маніфест «Плющ» (`docs/hub/АРХІТЕКТУРНИЙ-МАНІФЕСТ-ПЛЮЩ.uk.md` / `docs/hub/ARCHITECTUURMANIFEST-KLIMOP.nl.md`, досьє `orchestratie/onderwerpen/ecosysteem-klimop.json`). Короткий контекст `orchestratie/CONTEXT-COMPACT.md` — покажчик, а не підтвердження встановленого стану.
2. Визнач, яку службу стосується завдання. Для користувацької частини шукай у `src/`, для серверної — в `backend/` та `server/`, для спільних правил — у `shared/`, для розгортання — у `deploy/`, для бази — в `migrations/`.
3. Перевір чинні маршрути, права доступу й пов'язані випробування. Назви файли й функції, які фактично забезпечують роботу.
4. За вимогами Етапу 0 маніфесту «Плющ» (§3.3, §45) чітко відрізняй можливість, **описану в цільовій документації**, від можливості, **впровадженої в коді**, та від можливості, **підтвердженої на живому сайті**. Наявність файла у сховищі ніколи не прирівнюється до роботи наживо.
5. Звір `voornaamst`, `integratie` і поточну встановлену версію. Якщо немає доступу до сервера, не видавай дані зі сховища за стан робочої системи.
6. Сформулюй карту залежностей, приховані єдині точки відмови (§42 маніфесту «Плющ») і найменший безпечний наступний крок. Не змінюй файли лише заради огляду.

## Результат

Стислий опис служби, знайдені джерела, що справді працює наживо, що є цільовою концепцією «Плющ», що не перевірено, залежності та пропонований наступний крок. Права доступу до служб визначають чинні дозволи підключення MCP, а не ця навичка.
