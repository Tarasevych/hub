# Підготовка та встановлення випусків Mijn Ruimte

## Коли застосовувати

Застосовуй цю навичку, коли власник просить підготувати оновлення сайту, зібрати випуск, опублікувати архів у GitHub, передати його до встановлення, перевірити встановлення або відновити попередню версію.

Навичка пояснює послідовність роботи. Вона **не надає дозволів**, не дозволяє обійти ключ доступу власника та не замінює чинні правила.

## Джерела істини

Перед діями перечитай:
- `AGENTS.md` та `orchestratie/beleid.json` — канонічні правила і порядок координації.
- `orchestratie/CONTEXT-COMPACT.md` — короткий покажчик, але перевір його актуальність за правилами.
- `deploy/ПРАВИЛА-ПАКЕТА-РОЗГОРТАННЯ.uk.md` — обов'язкові складники пакета.
- `backend/uitrol-goedkeuring.ts` — приймання архіву, попередня перевірка, погодження.
- `backend/uitrol-voorcontrole.ts` — перевірки архіву.
- `backend/uitrol-ontwikkelarchief.ts` — підтвердження походження випуску.
- `backend/uitrol-github.ts` — публікація й місцеве збереження архівів.

Якщо вказівки відрізняються, не вгадуй: чинні захищені правила й фактичний стан сервера мають перевагу над цією навичкою.

## Обов'язкова послідовність

1. Визнач завдання, права свого підключення й актуальну робочу основу. Перевір стан `voornaamst` та `integratie`, потім, за наявності доступу, звір справжню версію сайту через `/api/version`. Якщо гілки розійшлися або база застаріла, не зливай і не встановлюй навмання.
2. Зареєструй завдання у чинній координації. Працюй у власній гілці, не змінюй чужі гілки чи захищені правила. Перед змінами виконай передбачені перевірки актуальності.
3. Підготуй зміни, пов'язані перевірки, перелік змінених файлів та пояснення наслідків. Нічого не вилучай лише для того, щоб перевірки стали успішними.
4. Перед підготовкою випуску перевір правила, залежності, стан бази даних, результати випробувань, відповідність випуску встановленій версії та можливість відновлення. Невиконані перевірки назви прямо.
5. Використовуй чинний конвеєр координації й складання, а не вигадуй інший формат архіву. Збережи повну фіксацію змін, обов'язкові відомості, журнал походження, відбиток SHA-256 та результати перевірок.
6. Публікацію у GitHub вважай завершеною лише після перевірки, що в потрібному випуску справді існує відповідний архів із точним відбитком. Стан «опубліковано» не означає «встановлено».
7. Передай архів лише через дозволений канал. Сервер повинен перевірити його **до** відображення дії «Схвалити й встановити». У поточному коді наявне передавання частинами; пряме отримання архіву сервером із GitHub є **запланованою, але ще не впровадженою** можливістю.
8. Встановлення здійснюється лише після окремого підтвердження власником згідно з чинним правилом ключа доступу. Агент не підтверджує власне встановлення, не підробляє погодження і не розширює свої повноваження.
9. Звір результат із журналом установлених випусків, справжньою версією сайту, перевірками працездатності та станом відновлення. Якщо встановлення не завершилося, не називай його успішним.
10. Після завершення онови звіт та запропонуй зміни до навички, якщо чинні інструкції застаріли. Зміни канонічних правил потребують окремого погодження.

## Доставлення архіву без пристрою власника — запланований напрям

Потрібний ланцюжок: перевірений випуск GitHub → сервер сам отримує архів → звіряє SHA-256, походження й передумови → створює звичайну пропозицію встановлення → власник підтверджує ключем доступу → наявний встановлювач виконує роботу.

**Поки серверне отримання з GitHub не впроваджено, не стверджуй, що цей ланцюжок уже працює.** Не додавай обхідних шляхів, які виконують установлення без погодження.

## Незалежні копії та Telegram — запланований напрям

Після успішного встановлення необхідно мати щонайменше місцевий архів, підтверджений архів у GitHub та, за окремою згодою власника, зашифровану копію в особистому Telegram. Додай опис змін, версію, фіксацію змін, відбиток SHA-256, дату й статус встановлення. Наявний бот Telegram призначений насамперед для входу та повідомлень: **надсилання архівів поки не підключено**.

Не передавай у Telegram ключі, маркери доступу, особисті дані, вміст пошти, незашифровані запасні копії або архіви з такими даними. Не вважай посилання на GitHub другою збереженою копією. Враховуй обмеження розміру файла в інтерфейсі бота; у разі перевищення розміру використовуй перевірене розбиття за частинами із загальним відбитком і перевіркою повноти.

## Повідомлення власникові

Завжди розділяй стани: «підготовлено», «опубліковано», «завантажено на сервер», «перевірено», «очікує погодження», «встановлено», «збережено в Telegram». Кожен стан повідомляй лише після підтвердження відповідною системою. Якщо копію до Telegram не передано, не приховуй цієї обставини.

## Умови перегляду навички

Переглядай навичку після змін конвеєра випусків, правил погодження, форматів архівів, адрес підключення, механізмів перевірки походження або засобів збереження. Спочатку порівнюй попередню й нову редакції; не скасовуй захисні вимоги як «застарілі» без окремого рішення власника.
