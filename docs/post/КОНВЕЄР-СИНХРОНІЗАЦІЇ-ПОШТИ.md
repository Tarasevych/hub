# Конвеєр синхронізації Пошти v1

## 1. Скінченний автомат станів

```text
authorization_required
→ connecting
→ initial_sync
→ connected
↘ degraded / reauth_required / error
→ disconnected
```

Статус `connected` вимагає: підтвердженої ідентичності постачальника, зашифрованого оновлення-маркера доступу, активного watch/підписки, завершеної початкової синхронізації та дійсного курсора.

## 2. Конвеєр під'єднання постачальника

1. Користувач явно натискає «Під'єднати Gmail/Microsoft».
2. Серверна частина перевіряє канонічну сеанс Пошти та право власності на обліковий запис.
3. Шлюз готовності (readiness пропускний бар'єр) перевіряє конфігурацію клієнта, ключ шифрування, білий список зворотний виклик-адрес та політику постачальника.
4. Створюється хешований стан OAuth постачальника з обмеженим терміном дії, PKCE та точними областями доступу (обсяги повноважень).
5. Перехід у тій самій вкладці або схваленому спливному вікні запускає отримання згоди у постачальника; в URL немає жодних маркерів доступу чи доказів, окрім коду/стану постачальника.
6. Зворотний виклик (зворотний виклик) захоплює стан із короткостроковою орендою обробки (processing тимчасове право).
7. Сервер виконує обмін коду на маркери доступу.
8. Перевіряється відповідність ідентичності постачальника політиці вибраного або нового облікового запису.
9. Refresh-маркер доступу шифрується за допомогою AES-256-GCM та AAD.
10. Області доступу/статус облікового запису та маркер доступу фіксуються атомарно.
11. Створюється watch/підписка.
12. У чергу ставиться завдання початкової синхронізації.
13. Відбувається повернення до розділу Поштові облікові записи із правдивим станом прогресу.
14. Через websocket публікується ревізія облікового запису.

Збій до фіксації маркера доступу залишає статус `authorization_required`; збій після фіксації маркера доступу, але до завершення синхронізації, залишає статус `degraded`/`initial_sync` і ніколи хибно не встановлює `connected`.

## 3. Шлях Gmail push → Інтерфейс (UI)

```text
Gmail mailbox change
→ Gmail API publishes Pub/Sub message
→ authenticated Pub/Sub push POST
→ validate OIDC JWT audience/issuer/expiry
→ decode envelope and validate emailAddress/historyId
→ dedupe provider messageId
→ resolve owner-scoped mail_account
→ enqueue/coalesce provider.sync.incremental
→ return 2xx

worker claims incremental job
→ refresh access token under account lease
→ users.history.list(startHistoryId=stored cursor)
→ collect added/deleted/label deltas
→ fetch changed messages
→ parse MIME with bounded limits
→ upsert messages, bodies, labels, attachments, threads
→ commit next historyId only after all durable writes
→ enqueue neuro jobs for changed content hash
→ evaluate calm notification threshold
→ publish entity.update revision
→ UI refetches normalized owner-scoped data
```

Тіло push-запиту не розглядається як вміст повідомлення. Дубльовані або невпорядковані сповіщення є безпечними, оскільки синхронізація починається зі збереженого курсора, а операції запису є ідемпотентними.

## 4. Початкова синхронізація Gmail

### 4.1 Підготовка

- статус облікового запису переводиться в `initial_sync`;
- спочатку створюється/поновлюється watch, щоб мінімізувати проміжок можливих змін;
- зберігається час закінчення дії watch та базовий рівень історії (history baseline);
- створюється одне завдання початкової синхронізації з ключем ідемпотентності облікового запису.

### 4.2 Мітки

- завантаження списку міток;
- відображення системних і користувацьких міток постачальника;
- upsert за парою `(account, provider_label_id)`;
- збереження невідомих міток постачальника замість їх відкидання.

### 4.3 Повідомлення

- посторінкова розбивка ідентифікаторів повідомлень із використанням обмеженого розміру сторінки;
- фіксація контрольної точки (контрольна точка) маркера доступу сторінки окремо від фінального курсора історії;
- завантаження вмісту повідомлень з обмеженням паралельності та частоти запитів (rate limit);
- нормалізація заголовків та адрес;
- рекурсивний розбір MIME з обмеженнями на глибину, кількість частин та розмір декодованих даних;
- надання переваги `text/plain`; очищення HTML; блокування зовнішніх зображень;
- запис метаданих вкладень; байти великих вкладень вивантажуються відкладеними (lazy) завданнями;
- upsert повідомлення за ідентифікатором постачальника;
- прив’язка до ланцюжка постачальника;
- відображення міток;
- оновлення лічильників та часової мітки останнього повідомлення в ланцюжку.

### 4.4 Завершення

- вичерпання всіх сторінок посторінкової розбивки;
- узгодження видалень лише в межах явно визначеної області синхронізації;
- фіксація початкового курсора та часової мітки завершення;
- встановлення статусу облікового запису `connected`, якщо watch залишається дійсним;
- постановка в чергу нейрозавдань лише для змінених хешів вмісту;
- публікація ревізії.

Безпека перезапуску: завдання може повторно обробити сторінку без створення дублікатів повідомлень, оскільки ідентифікатори постачальника та ключі ідемпотентності є унікальними.

## 5. Деталі інкрементальної синхронізації Gmail

Зміни історії, що обробляються:

- `messagesAdded`: завантаження та upsert повних метаданих/вмісту;
- `messagesDeleted`: позначення видалення у постачальника (tombstone);
- `labelsAdded`: upsert зв’язку;
- `labelsRemoved`: видалення зв’язку;
- зміни лише з ідентифікатором повідомлення: завантаження поточного стану від постачальника.

Правила роботи з курсором:

- одна активна оренда (тимчасове право) на обліковий запис;
- сторінки історії обробляються послідовно;
- курсор не просувається у разі збою на сторінці;
- фінальний курсор використовує авторитетний результат відповіді історії;
- недійсний `startHistoryId` встановлює прапорець відновлення та планує обмежений повторний початковий запуск;
- періодичний резервний механізм працює навіть за активного push-потоку.

## 6. Життєвий цикл Gmail watch

- `users.watch` створюється після отримання згоди та фіксації маркера доступу;
- зберігається час закінчення дії (expiration);
- щоденне завдання поновлення;
- термінове поновлення, коли час закінчення дії наближається;
- виклик `users.stop` при вимкненні облікового запису, де це доречно;
- помилка watch не видаляє дані поштової скриньки;
- прострочений watch змінює статус на `degraded`, а резервна синхронізація продовжує роботу.

## 7. Шлях сповіщення Microsoft → Інтерфейс (UI)

```text
Graph change notification
→ HTTPS webhook
→ validationToken branch returns exact plain text
→ normal branch validates clientState and subscription
→ dedupe notification
→ enqueue account/folder delta job
→ 2xx

worker
→ refresh token
→ follow stored deltaLink
→ page through changes
→ upsert/delete messages and folders
→ persist nextLink while paging
→ commit final deltaLink after durable completion
→ neuro jobs + notifications + websocket revision
```

Підписки поновлюються до закінчення терміну їхньої дії. Події життєвого циклу запускають повторну авторизацію або перестворення підписки залежно від ситуації.

## 8. Контракт аналізатора MIME

Вхідні дані вважаються недовіреними. Обмеження:

- максимальний розмір сирого повідомлення в байтах;
- максимальна глибина вкладень MIME;
- максимальна кількість частин (parts);
- максимальний розмір декодованої частини;
- обмежена кількість та довжина заголовків;
- білий список кодувань символів (charset allowlist) та резервне кодування;
- жодного виконання сценаріїв;
- очищувач HTML;
- блокування зовнішніх зображень;
- посилання `cid:` переписуються лише на перевірені локальні вкладення;
- нормалізація небезпечних імен файлів;
- розпакування архівів під час поглинання даних вимкнено.

Результат роботи аналізатора зберігає попередження. Пошкоджене тіло листа не відкидає базову інформацію про відправника, тему, дату та ідентичність постачальника.

## 9. Побудовник ланцюжків

Первинним ключем є ідентифікатор ланцюжка/розмови постачальника. Внутрішній побудовник:

- виконує upsert ланцюжка;
- зв’язує повідомлення;
- обчислює часову мітку останнього листа, лічильники непрочитаних/усіх повідомлень та список учасників;
- зберігає семантику постачальника;
- не об’єднує евристично непов’язані ланцюжки постачальника;
- повідомлення ручного імпорту можуть використовувати окремий синтетичний ідентифікатор ланцюжка.

## 10. Відображувач міток

Внутрішні мітки зберігають ідентичність постачальника та відкривають нормалізовані можливості:

- вхідні (скринька вхідних);
- непрочитане/прочитане (unread/read);
- надіслані (sent);
- чернетки (чернетка);
- кошик/видалені (trash/deleted);
- спам/небажана пошта (spam/junk);
- із зірочкою/прапорцем (starred/flagged);
- користувацька мітка / тека / категорія.

Дії запису у постачальника є командами перехідника з підтримкою ідемпотентності та аудиту. Тріаж в інтерфейсі відокремлений від міток постачальника, якщо користувач явно не ввімкнув правило відображення.

## 11. Конвеєр обробки вкладень

1. Збереження метаданих під час розбору повідомлення.
2. Політика визначає негайне (eager) або відкладене (lazy) завантаження.
3. Фоновий виконавець завантаження перевіряє право власності на обліковий запис/повідомлення та маркер доступу.
4. Потокове завантаження з обмеженням розміру; обчислення SHA-256.
5. Збереження за приватним шляхом в об’єктному сховищі.
6. Сканування/класифікація; встановлення мітки `clean` / `blocked` / `unsupported`.
7. Інтерфейс ніколи не відкриває доступ до байтів до отримання безпечного статусу.
8. Очищення при вимкненні облікового запису або за політикою зберігання видаляє об’єкти ідемпотентно.

## 12. Нейроінклюзивний конвеєр

### 12.1 Детермінований прохід

- індикатори інформаційного шуму;
- вилучення даних про відправника та контекст;
- дати та фрази, що вказують на необхідність дії;
- детерміновані сегменти цитування;
- консервативна пропозиція тріажу;
- хеш вмісту.

### 12.2 Прохід ШІ

Виконується лише на зміненому, очищеному тексті обмеженого розміру:

- системна інструкція трактує лист виключно як дані, і ніколи як команди до виконання;
- вивід за схемою містить поля хто/що/коли/наступна дія, рівень впевненості та посилання на цитати;
- посилання повинні вказувати на збережені сегменти джерела;
- недійсні цитати відхиляють артефакт;
- результат завжди має `requires_review=true`;
- жодні інструменти для мутації даних у постачальника недоступні.

### 12.3 Проєкція в інтерфейсі

- Режим фокусування (Focus View) показує одне повідомлення;
- режим низької енергії відкриває лише дії відповісти / створити завдання / відкласти (відкладення);
- тихе збереження контексту відновлення фіксує точне повідомлення/ланцюжок/стан панелі без нав’язливих запитів чи бічних панелей;
- стани До дії / Очікування / Інфо / Пізніше (Action/Waiting/Info/Later) залишаються відкритими для виправлення користувачем;
- м’які нагадування використовують спокійні пороги спрацьовування;
- жодних червоних лічильників накопиченої пошти.

## 13. Конвеєр надсилання

```text
user edits draft
→ save local/provider draft
→ POST send/prepare
→ validate recipients, account capability, draft revision
→ render exact preview and compute payload hash
→ create short-lived prepared command
→ UI asks explicit confirmation
→ POST send/confirm with command id + confirmation token/hash
→ claim command once
→ provider send with idempotency strategy
→ reconcile provider result
→ store sent message/thread update
→ audit and publish revision
```

Час очікування після виклику постачальника є неоднозначним: фоновий виконавець перевіряє наявність повідомлення у постачальника та докази ідемпотентності перед повторною спробою. Автоматичне надсилання через ШІ, нагадування, фонову чергу або скорочення режиму низької енергії заборонено.

## 14. Політика повторних спроб та обмеження частоти запитів

- специфічна для постачальника класифікація кодів (`401`, `403`, `404 cursor`, `409`, `429`, `5xx`);
- експоненційна затримка (exponential backoff) + випадкове відхилення (jitter);
- дотримання заголовка `Retry-After`;
- обмеження паралельності на рівні облікового запису;
- блокування (lock) на оновлення маркера доступу;
- відокремлення легкої синхронізації від збагачення даними ШІ;
- застарілий інтерфейс залишається доступним для читання під час збою на боці постачальника;
- записи dead-letter зберігають безпечний код помилки, а не вміст повідомлення чи маркер доступу.

## 16. Спостережуваність

Для кожного облікового запису відстежуються:

- час останнього push-сповіщення та останньої резервної синхронізації;
- час закінчення дії watch/підписки;
- вік курсора;
- глибина черги / повторні спроби / мертві завдання (dead завдання);
- кількість змінених повідомлень;
- попередження аналізатора;
- результат оновлення маркера доступу;
- стан обмеження частоти запитів (rate-limit);
- ревізія websocket;
- лічильники відповідності критеріям сповіщень без каральних формулювань в інтерфейсі користувача.

Операційні метрики чітко відокремлені від доброзичливих текстів користувацького інтерфейсу.
