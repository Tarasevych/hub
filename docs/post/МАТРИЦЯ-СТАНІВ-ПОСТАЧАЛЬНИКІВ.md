# МАТРИЦЯ СТАНІВ ПОСТАЧАЛЬНИКА (ПОСТАЧАЛЬНИК СТАН MATRIX) — N‑21, кроки 1–3

- Дата фіксації: 2026‑08‑12; OPEN‑015 повторно звірено 2026‑08‑25.
- Середовище виконання-база перед N‑21 кроками 2–3: Версія ID `1786319470714`.
- Офіційна Gmail REST surface повторно звірена 2026‑08‑25; нові Classification Мітки зафіксовано окремо й не змішано зі звичайними Gmail labels.
- Обсяг: канонічна спроможність-safe матриця §4.11 + межа відкладення D‑22 + збіжність станів N‑21. Gmail Відкладення є read-проєкцією постачальник→UI без дедлайну повернення; локальний відкладення залишається суто локальним (local-only). Двостороння синхронізація вимагається тільки для фактично задокументованих можливостей запису (запис спроможності) Gmail.
- Статуси нижче: **ПОТОЧНИЙ** — підтверджено кодом; **ЦІЛЬОВИЙ СТАН** — контракт для наступного окремого кроку; **BLOCKED** — команду не можна надсилати без підтвердженої спроможності (спроможність).

## 1. Межа відповідальності

Наш сервіс є надмножиною Gmail: спільні поштові стани можуть сходитися з постачальником, а локальні UX-стани залишаються нашими. Локальний стан не маскується під стан Gmail.

- Спільні стани: read/unread, star, скринька вхідних/archive, trash, spam, користувацькі мітки Gmail (користувач мітки). Для Gmail відкладення доступна лише read-проєкція належності (membership) через офіційний пошуковий запит; запис (запис) — тільки якщо з’явиться офіційно підтримана спроможність.
- Локальні стани: поточний відкладення `mail_snoozes_v1` і його значок стану/UI залишку часу, піктограми локальних міток, щільність інтерфейсу (density), панель читання (reading pane), групування ланцюжків (ланцюжок grouping), кольори рядків, правила відправників (sender правила), сигнали пріоритету, налаштування згортання/навігації.
- Проєкція постачальника (Постачальник projection): список повідомлень, `labelIds`, подання робочої області категорій (category work-area view), лічильники непрочитаних, належність до Gmail `in:snoozed` без дедлайну, `historyId` там, де він доступний, та нормалізований приватний кеш — це проєкція Gmail, а не окремий авторитетний стан.
- Жодний локальний UX-стан не повинен породжувати виклик Gmail API.

## 3. Шлюз спроможностей (Capability пропускний бар'єр) перед будь-якою командою постачальника

Команда може покинути сервіс лише тоді, коли пройдені всі перевірки:

1. `provider === google`, обліковий запис належить поточному власнику і є доступним.
2. Операція наявна в явній карті дій постачальника; жодних вгадуваних міток чи маршрутів.
3. Наявна необхідна область доступу / спроможність: для стану повідомлення — `modify`; для визначення мітки — спроможність CRUD для міток.
4. Наявний ідентифікатор сутності постачальника; локальні ідентифікатори ніколи не надсилаються як ідентифікатори Gmail.
5. Системна мітка допускає цю зміну. `SENT`/`DRAFT` не змінюються через загальну команду міток; чернетки не отримують міток. Classification Мітки є окремою схемою/спроможність і не проходять через поточний контракт `addLabelIds/removeLabelIds`.
6. Пакет (batch) розбито в межах офіційного ліміту: `batchModify` — максимум 1000 ідентифікаторів повідомлень; поодинокий `modify` — до 100 доданих і 100 видалених ідентифікаторів міток.
7. Для читання Gmail відкладення дозволено лише явний виклик `messages.list?q=in:snoozed`; шлюз запису завжди повертає `unsupported`, дедлайн — `unavailable`, до появи офіційно задокументованої спроможність.
8. Відмова на шлюзі спроможностей не змінює оптимістичний UI на успішний і не запускає повторних спроб.

## 4. Контракт часових міток і розв’язання конфліктів (ЦІЛЬОВИЙ СТАН)

- Порівнюється лише той самий ключ стану одного власника/облікового запису/постачальника/сутності, наприклад `message:123:unread`.
- Часова мітка клієнта є контекстом, а не джерелом істини. Локальна команда отримує авторитетний час `serverAcceptedAt`.
- Подія постачальника отримує `providerObservedAt`; `historyId` використовується для визначення порядку тільки всередині однієї поштової скриньки Gmail. Його не можна порівнювати між обліковими записами і не можна трактувати як астрономічний час (wall-clock timestamp).
- Поле `internalDate` повідомлення не використовується для впорядкування мутацій стану.
- Правило: перемагає найновіша подія за порівнюваним авторитетним часом. Якщо порядок неможливо довести, виконується оновлення/узгодження (оновлення/узгодження), конфлікт фіксується як розбіжність (divergence), а сліпе перезаписування заборонено.
- Якщо бажаний стан вже дорівнює стану постачальника, це вважається збіжністю (convergence): команда завершується без додаткового запису.

## 5. Контракт ідемпотентності (ПОТОЧНИЙ для поодиноких read/star/archive; ЦІЛЬОВИЙ СТАН для решти)

- Кожен намір користувача або системи має стабільний `intentId`; повторна доставка цього самого наміру використовує той самий `idempotencyKey`.
- Область дії ключа: власник + обліковий запис + постачальник + ID сутності + ключ стану + ID наміру. Новий намір користувача отримує новий ID, навіть якщо бажане значення збігається.
- Команди стану описують бажане кінцеве значення, а не перемикання (`toggle`). `toggle` дозволений лише в інтерфейсі; перед записом у постачальника він перетворюється на явне `true/false` або набір додавання/видалення.
- Поточна 30‑секундна дія «Скасувати» (Undo) є UX інверсною командою в пам’яті вкладки; вона не є надійним записом ідемпотентності, реєстром намірів чи outbox-чергою.
- Після часу очікування або невідомого результату обов’язковим є читання після запису та узгодження (read-after-write/узгодження).
- Створення мітки, надсилання листа та остаточне видалення не можна сліпо повторювати як звичайні встановлення стану. Для створення мітки спочатку звіряються запис наміру та каталог постачальника. Надсилання/outbox не входить у цей крок.

## 6. Контракт повторних спроб, повернення стану та аудиту (ПОТОЧНИЙ для outbox станів; ЦІЛЬОВИЙ СТАН для решти)

- Повторні спроби (Повторна спроба): мережеві збої, 408, 429 та 5xx; експоненційна затримка з випадковим відхиленням (exponential backoff + jitter); обов’язкове врахування `Retry-After`.
- Без сліпих повторів: помилка перевірки коректності 400, брак прав/області доступу 403, застаріла/відсутня сутність 404, непідтримувана дія. Код 401 переводить спроможність у стан `auth-required` до окремого потоку авторизації власника; цей документ не запускає авторизацію.
- Код 404 для курсора історії Gmail означає необхідність повної синхронізації, а не повторення запиту зі старим курсором.
- Після остаточного збою оптимістична проєкція повертається до попереднього стану до свіжого стану постачальника/локального стану з видимим статусом, а не залишається відображеною як успішна.
- Надійний запис аудиту має містити: власника/обліковий запис/постачальника, ключ дії/стану, цільові ідентифікатори постачальника, відбиток бажаного стану, джерело, ідентифікатори наміру/ідемпотентності, час прийняття/спостереження/завершення, номер спроби, підсумок та безпечний код помилки.
- Аудит ніколи не містить OAuth-маркерів доступу, сирих заголовків, тіла листа, теми, фрагмента тексту (snippet), вмісту вкладень або списків отримувачів.

## 7. Поточні середовище виконання-факти та відкриті прогалини (gaps)

1. `backend/google-suite-mail-browser.ts` виконує поточні поодинокі та масові мутації напряму й повертає нормалізоване постачальником повідомлення; білий список дій: read, unread, archive, скринька вхідних, trash, untrash, star, unstar, мітка, move, unlabel.
2. У N‑21 поодинокі дії рядка read/star/archive оновлюють латкою проєкцію + приватний кеш до надсилання і створюють запис у `mail_state_intents_v1`; проміжний результат залишається видимим як `pending`, опитування статусу та сервісний планувальник розкладу повторюють його, а термінальний збій повертає збережений рядок/кеш. Масові дії (bulk) та інверсний Undo поки що зберігають попередній прямий контракт.
3. Подання категорій D‑17 окремо завантажує відповідні рядки на базі постачальника та живий лічильник; попередній перегляд/фільтр не є мутацією поштової скриньки та не породжує наміру повторної спроби.
4. D‑22: `backend/mail-uitstel.ts` залишається суто локальним і повертає межу спроможностей; окремо `messages.list?q=in:snoozed` проєктує першу сторінку належності Gmail в інтерфейс без дедлайну повернення та без запису.
5. `backend/mail-weergave-voorkeuren.ts` обслуговує локальні налаштування з ізоляцією за власником; Gmail API при цьому не викликається.
6. D‑13 реалізував спільний датований знімок `gmail.labels.get` для лічильників робочого простору й бічної панелі та узгодження після підтверджених мутацій/Undo/Оновлення; застарілі відповіді відсікаються.
7. `backend/mail-platform.ts` тепер містить явний контракт станів/дій/спроможностей, стабільний ключ ідемпотентності наміру та експоненційні повторні спроби з jitter; `google-suite-mail-browser.ts` реалізує ізольований за власником/обліковим записом outbox, оренду (тимчасове право), збіжність read-before-write, заміщення старіших намірів (supersede) та компактний аудит подій без створення другого сховища маркерів доступу.
8. Наявні планувальник розкладу-завдання синхронізації/обслуговування не доводять виконання двостороннього контракту команд стану; їх не слід позначати як реалізацію N‑21.
9. Встановлення та скасування відкладення напряму фіксуються в `mail_snoozes_v1`; загальний контракт намірів стану зберігає спроможність відкладення у постачальника як `unsupported`, але не використовується як другий шар збереження для локального відкладення. Виклики постачальника та повторні спроби не виконуються.

## 8. Офіційна база документації Gmail API

Повторно перевірено 2026‑08‑25 за офіційною документацією Google Workspace. Висновок про відсутність публічної спроможності запису відкладення/unsnooze та API дедлайну повернення є логічним висновком з актуального переліку публічних REST-методів і задокументованої семантики міток, а не твердженням про внутрішню будову інтерфейсу Gmail.

- [users.messages.modify](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/modify) — додавання/видалення міток, до 100 ідентифікаторів міток за одне оновлення.
- [users.messages.batchModify](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/batchModify) — до 1000 ідентифікаторів повідомлень.
- [Manage мітки](https://developers.google.com/workspace/gmail/api/guides/labels) — системні мітки, які можна застосовувати, та обмеження для системних міток і чернеток.
- [users.labels resource](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.labels) — семантика користувацьких/системних міток та операції CRUD.
- [users.history.list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.history/list) — семантика курсора; помилка 404 вимагає повної синхронізації.
- [users.messages resource](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages) — актуальний перелік публічних методів та окремі `classificationLabelValues`; поточний застосунок їх не реалізує.
- [Gmail REST v1 surface](https://developers.google.com/workspace/gmail/api/reference/rest) — публічні маршрути; на дату перевірки метод відкладення у переліку відсутній.
- [Filtering та searching повідомлення](https://developers.google.com/workspace/gmail/api/guides/filtering) та [users.messages.list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list) — параметр `q` приймає формат пошукового рядка Gmail.
- [Gmail пошук operators](https://support.google.com/mail/answer/7190?co=GENIE.Platform%3DDesktop&hl=en) — офіційно описує оператор `in:snoozed`; D‑22 використовує його лише для читання належності.
