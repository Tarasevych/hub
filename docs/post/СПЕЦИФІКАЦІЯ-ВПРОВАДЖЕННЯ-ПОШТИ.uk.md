# Технічна специфікація платформи Пошти v1

## 1. Словник статусів

- `confirmed`: підтверджено застосованим вихідним кодом та доказами на рівні панелі керування (control-plane).
- `partial`: реалізація існує, але зовнішні/оглядачеві докази неповні.
- `unverified`: цільовий стан або конфігурація ще не були випробувані на практиці.
- `blocked`: відсутній необхідний зовнішній конфігураційний або безпековий шлюз (пропускний бар'єр).
- `deprecated`: зберігається виключно для повернення стану або міграції.

Поточна базова лінія (baseline):

- Ручний/QA інтерфейс Пошта (фаза 1): confirmed.
- Реєстр/готовність постачальників M-110, самотестування конвертів AES-256-GCM та порожній уніфікований фасад читання з ізоляцією за власником (власник-scoped): confirmed.
- Автентифікований вхідний потік Gmail Pub/Sub, дедуплікація/коалесценція, оновлення маркерів доступу, поновлення watch, обмежена початкова/історична синхронізація читання та проєкція постачальника у Вхідні (Скринька вхідних): реалізовано за шлюзами середовища виконання (середовище виконання) та зовнішніх кінцевих точок; зовнішньо не випробувано.
- Надійний зовнішній планувальник та поглинання даних постачальника (ingestion): не активні.
- Кодовий шлях стану OAuth поштової скриньки Google / PKCE / поза мережею-згоди / зворотний виклик / фіксації маркера доступу: реалізовано за захищеними (закриття при збої) робоче середовище-шлюзами; зовнішня згода ще не випробувана.
- Мутація міток Gmail з ізоляцією за власником та явні двофазні кодові шляхи команди надсилання: реалізовано за шлюзами під'єднаного середовища виконання; поведінка запису у постачальника зовнішньо не випробувана.
- Microsoft Graph OAuth, фіксація зашифрованого оновлення-маркера доступу, перевірка поштової скриньки `/me`, перевірка коректності вебвикликів/`clientState`, синхронізація за delta-посиланнями та надсилання/мітки через постачальника: реалізовано за захищеними (закриття при збої) зовнішніми/середовище виконання-шлюзами; зовнішньо не випробувано.
- Диспетчеризація середовища виконання та областей доступу (обсяги повноважень) для конкретного постачальника, вимкнення/відкликання (disconnect/відкликання), очищення маркерів доступу/підписок, стан здоров’я синхронізації, відновлення застарілих оренд (stale-тимчасове право відновлення), контракт планування обслуговування та інвентаризація міграції ручних/постачальницьких даних: реалізовано. Застарілі ручні/QA записи зберігаються до приймання реального постачальника.
- Сховище маркерів доступу постачальника (token сховище): не активне.
- Gmail watch/Pub/Sub: не активні.
- Вебвиклики/дельта Microsoft Graph: не активні.
- Високоризикове надсилання листів: вимкнено.

## 2. Робочі пакети

### M-100 Архітектура та контракти

Результати:

- архітектура платформи;
- схема бази даних;
- конвеєр синхронізації;
- контракти постачальників та безпеки;
- план реалізації та шлюзи приймання;
- блокувальний аудит складання.

Критерії приймання:

- документація наявна в репозиторії;
- маніфест випуску правдиво зазначає, що середовище виконання постачальника неактивне;
- повернення стану вказує на попередню застосовану версію;
- жодних змін у поведінці авторизації/сеансу/інтерфейсу;
- зафіксовані термінальні докази складання/Наскрізні.

### M-110 Фундамент поштових постачальників

Результати:

- типи реєстру постачальників;
- модель статусів облікового запису;
- оцінювач секретів/готовності;
- допоміжний модуль конвертів маркерів доступу AES-256-GCM із детермінованими самотестами;
- запис черги з ізоляцією за власником та допоміжний модуль ідемпотентності;
- уніфікований фасад API читання поверх поточних даних;
- поверхня правдивої готовності для адміністратора/системи.

Критерії приймання:

- відсутність секрету шифрування призводить до безпечної відмови (fails closed);
- жоден сирий маркер доступу не з’є в БД, публічній відповіді або журналі аудиту;
- власник A не може прочитати обліковий запис/повідомлення власника B;
- дубльований ключ ідемпотентності завдання створює одне логічне завдання;
- поточна ручна Фаза 1 залишається функціональною;
- статус постачальника ніколи не стає `connected` без доказу наявності маркера доступу/підписки/синхронізації.

### M-120 OAuth поштової скриньки Google

Результати:

- окремий стан OAuth постачальника, окремий від стану ідентичності;
- точні області доступу (обсяги повноважень) Gmail;
- PKCE, стан, безпечне повернення, поза мережею-доступ;
- серверний обмін коду;
- перевірка профілю постачальника;
- збереження зашифрованого оновлення-маркера доступу;
- збереження наданих областей доступу;
- відкликання/вимкнення;
- кнопка, під'єднана з розділу Поштові облікові записи.

Критерії приймання:

- явний натискання користувача є єдиним пусковою подією запуску;
- один натискання створює один стан;
- повторний виклик зворотний виклик є ідемпотентним;
- невідповідність стану / закінчення терміну дії / неправильний власник відхиляються;
- оновлення-маркер доступу зашифрований із дійсним тегом GCM та AAD;
- оглядач не отримує жодного маркера доступу;
- відмова у згоді залишає статус `authorization_required`;
- реальна згода в Chrome та повернення підтверджені власником;
- задокументовано статус верифікації обмежених областей доступу (обмежений обсяги повноважень) Google.

Зовнішні передумови:

- OAuth-клієнт дозволяє точний URI зворотного виклику (зворотний виклик);
- налаштовано екран згоди та області доступу;
- пройдено верифікацію обмежених областей доступу / оцінку безпеки за потреби;
- налаштовано `MAIL_TOKEN_ENCRYPTION_KEY_V1`.

### M-130 Gmail watch та Pub/Sub

Результати:

- записи конфігурації теми/підписки (topic/subscription);
- автентифікована push-кінцева точка;
- перевірка коректності аудиторії/емітента (audience/issuer) JWT;
- дедуплікація повідомлень Pub/Sub;
- створення/поновлення/зупинка `users.watch`;
- щоденний планувальник розкладу поновлення;
- резервний планувальник розкладу синхронізації;
- статус здоров’я/готовності.

Критерії приймання:

- підроблений/непідписаний push або push із неправильною аудиторією відхиляється;
- дійсний тестовий push ставить у чергу одне об’єднане (coalesced) завдання для облікового запису;
- дубльований `messageId` ігнорується без побічних ефектів (no-op);
- обробник вебвиклику не виконує вбудованого (inline) завантаження поштової скриньки;
- час закінчення дії watch зберігається та поновлюється;
- пропуск push-сповіщень відновлюється резервним механізмом;
- зафіксовано реальну доставку через Google Pub/Sub.

Зовнішні передумови:

- проєкт/тема Google Cloud;
- дозвіл сервісного облікового запису публікатора Gmail;
- автентифікована push-підписка та аудиторія;
- перевірений зовнішній POST-маршрут AppDeploy/власного домену.

### M-140 Фонові виконавці синхронізації Gmail

Результати:

- оренда оновлення маркера доступу;
- синхронізація міток;
- початкова посторінкова розбивка повідомлень;
- інкрементальна синхронізація історії;
- аналізатор MIME;
- upsert повідомлень/ланцюжків/міток;
- метадані/завантаження вкладень;
- скидання курсора відновлення;
- ревізія через websocket.

Критерії приймання:

- перезапуск під час обробки сторінки є ідемпотентним;
- курсор просувається лише після фіксації змін (фіксація змін);
- дубльовані ідентифікатори постачальника не створюють дублікатів записів;
- додавання/видалення міток та видалення листів відображаються коректно;
- пошкоджений MIME не призводить до аварійного завершення синхронізації облікового запису;
- недійсний курсор історії запускає обмежене відновлення;
- негативні тести ізоляції за власником проходять успішно;
- інтерфейс отримує реальний лист без ручного імпорту.

### M-150 Уніфікований API Пошти

Нормативні операції:

- список облікових записів;
- список/отримання повідомлень;
- список/отримання ланцюжків;
- список міток;
- зміна міток постачальника / стану прочитання;
- збереження чернетки;
- підготовка/підтвердження надсилання;
- вимкнення облікового запису;
- стан здоров’я синхронізації.

Критерії приймання:

- курсори посторінкової розбивки непрозорі (непрозорий) та прив’язані до власника;
- ідентифікатори облікових записів не можуть перетинати межі власників;
- фільтри запитів обмежені та перевіряються за білим списком (allowlisted);
- мутації ідемпотентні та записуються в аудит;
- надсилання вимагає явного короткоживучого підтвердження;
- помилки API використовують стабільні коди причин і ніколи не розкривають маркери доступу постачальника.

### M-160 Функціональні Вхідні (Функціональні Вхідні) на реальних даних

Результати:

- поточна Фаза 1 відображається на канонічні реальні повідомлення/ланцюжки;
- режим фокусування (Focus View), чотиристаноружий тріаж, рівень довіри з цитуванням (cited Trust Layer) та тихе збереження контексту відновлення працюють на даних постачальника;
- ручне джерело залишається візуально відмінним;
- оновлення через websocket;
- проєкція з урахуванням рівня енергії (energy-aware);
- відповідність критеріям спокійних сповіщень (calm notifications).

Критерії приймання:

- тема/тіло/цитати джерела постачальника збігаються з оригіналом;
- контекст поточного облікового запису стабільний під час оновлення сторінки/перемикання;
- не виникає зсувів макета (компонування shift);
- подання з низьким рівнем енергії показує не більше трьох основних дій;
- відсутні каральні лічильники чи формулювання;
- за відсутності ШІ система деградує до детермінованого виводу з цитатами;
- зовнішній вміст не може викликати інструмент або дію надсилання.

### M-170 Microsoft Graph

Результати:

- конфігурація реєстрації застосунку Microsoft;
- сховище маркерів доступу OAuth/PKCE/поза мережею;
- перевірка ідентичності через `/me`;
- дельта тек/повідомлень;
- перевірка коректності вебвикликів/`clientState`/життєвого циклу;
- поновлення підписок;
- відображення надсилання та міток/тек Graph;
- вимкнення облікового запису.

Критерії приймання дзеркально повторюють шлюзи безпеки/власника/ідемпотентності Google плюс реальні докази роботи вебвикликів і дельти Graph.

### M-180 Очищення та міграція

Результати:

- план міграції ручних записів `mail_items_v1`;
- сумісне читання (compatibility reads);
- прапорці функціональності (feature flags);
- інвентаризація мертвого коду;
- зберігання/експорт/видалення даних;
- репетиція повернення стану (відкочування rehearsal).

Критерії приймання:

- жодної втрати даних;
- ручні записи залишаються розрізнюваними;
- старі маршрути видаляються лише після аудиту використання та доказів;
- повернення стану відновлює попередній код без пошкодження нових записів.

## 3. Контракт API

### Облікові записи

```text
GET /mail/accounts
POST /mail/accounts/{id}/connect
POST /mail/accounts/{id}/disconnect
GET /mail/accounts/{id}/sync-health
```

Відповідь облікового запису містить лише безпечний статус спроможностей:

- id/постачальник/email/відображуване ім’я;
- назви наданих областей доступу (обсяги повноважень);
- статус;
- час останньої синхронізації;
- час закінчення дії watch/підписки;
- код причини повторної авторизації/помилки;
- ніколи не містить маркер доступу/шифротекст/IV/тег.

### Повідомлення та ланцюжки

```text
GET /mail/{accountId}/messages?cursor=&triage=&label=&unread=
GET /mail/{accountId}/messages/{messageId}
GET /mail/{accountId}/threads?cursor=
GET /mail/{accountId}/threads/{threadId}
```

Курсор посторінкової розбивки є підписаним/непрозорим і містить відбиток власника/облікового запису/фільтрів.

### Мітки

```text
POST /mail/{accountId}/labels
{
  "messageIds": ["..."],
  "add": ["..."],
  "remove": ["..."],
  "idempotencyKey": "..."
}
```

### Надсилання

Нормативний безпечний потік:

```text
POST /mail/{accountId}/send/prepare
POST /mail/{accountId}/send/confirm
```

Запитана єдина кінцева точка `/mail/{accountId}/send` може бути відкрита як фасад, але вона зобов’язана відхиляти виклики без дійсної підготовленої команди та явного підтвердження. ШІ не може надати підтвердження.

## 4. Інтерфейс реєстру постачальників

```ts
interface MailProviderAdapter {
  provider: 'google_gmail' | 'microsoft_graph';
  authorizationUrl(input: ProviderAuthorizationInput): Promise<ProviderAuthorizationResult>;
  exchangeCode(input: ProviderCallbackInput): Promise<ProviderTokenSet>;
  refreshToken(input: RefreshInput): Promise<ProviderAccessToken>;
  verifyMailbox(accessToken: string): Promise<ProviderMailboxIdentity>;
  createSubscription(ctx: ProviderContext): Promise<ProviderSubscription>;
  renewSubscription(ctx: ProviderContext): Promise<ProviderSubscription>;
  stopSubscription(ctx: ProviderContext): Promise<void>;
  initialSync(ctx: SyncContext): Promise<SyncPage>;
  incrementalSync(ctx: SyncContext): Promise<SyncPage>;
  fetchMessage(ctx: MessageFetchContext): Promise<ProviderMessage>;
  fetchAttachment(ctx: AttachmentFetchContext): Promise<ProviderAttachmentStream>;
  applyLabels(ctx: LabelMutationContext): Promise<ProviderMutationResult>;
  send(ctx: SendContext): Promise<ProviderSendResult>;
  revoke(ctx: ProviderContext): Promise<void>;
}
```

Перехідники повертають нейтральні щодо постачальника значення та стабільну класифікацію помилок; вони не записують стан UI напряму.

## 5. Набір приймальних тестів безпеки

Обов’язкові негативні тести:

- неправильний ідентифікатор власника/облікового запису;
- відсутня канонічна сеанс Пошти;
- повторне відтворення / закінчення терміну дії / підробка стану OAuth;
- неправильне джерело (origin) або шлях повернення зворотний виклик;
- відсутній/недійсний ключ шифрування;
- невідповідність AAD у GCM;
- стан гонитви (race condition) при одночасному оновленні маркера доступу;
- підроблений JWT у Pub/Sub;
- неправильний `clientState` у Graph;
- дубльована подія вебвиклику;
- відновлення після недійсного курсора;
- переповнення глибини/розміру MIME;
- очищення HTML-сценаріїв / зовнішніх зображень;
- невідповідність розміру/типу/хешу вкладення;
- prompt-ін’єкція з вимогою до ШІ надіслати листа або розкрити секрети;
- надсилання без підтвердження;
- дубльоване підтвердження надсилання;
- вимкнення облікового запису під час синхронізації, що перебуває в черзі.

## 6. Матриця тестування

1. Перше під'єднання Gmail: успіх / скасування / відмова в доступі.
2. Наявний обліковий запис ідентичності все одно вимагає окремої згоди для поштової скриньки.
3. Два облікові записи Gmail для одного власника.
4. Один і той самий email постачальника не може бути продубльований.
5. Власник A не має доступу до облікового запису/повідомлення/маркера доступу/завдання Власника B.

## 7. Контрольний список приймання в Chrome для кожного випуску постачальника

- жорстке оновлення (hard оновлення) сторінки Поштові облікові записи;
- під'єднання з одного явного натискання;
- перевірка точних областей доступу (обсяги повноважень) на екрані згоди;
- скасування та повторна спроба;
- повернення до того самого контексту поштового облікового запису;
- перевірка відсутності маркера доступу/коду в URL або сховищі оглядача;
- перевірка статусу прогресу облікового запису;
- отримання реального тестового листа;
- спостереження за оновленням інтерфейсу без ручного імпорту;
- натискання F5 та тихе відновлення контексту без нав’язливих запитів;
- перемикання облікового запису та підтвердження ізоляції даних;
- вимкнення облікового запису та перевірка зупинки синхронізації;
- повторення перевірки у вузькому вікні перегляду (видима область);
- перевірка вкладок Network/Console та доказів доставки в панелі керування постачальника.

## 8. Шлюзи розгортання

- Прапорці функціональності (feature flags) на рівні постачальника/облікового запису.
- Фундамент → канарковий випуск для власника → обмежена реальна поштова скринька → ширша активація.
- Кожен етап має прямий ідентифікатор версії для повернення стану.
- Міграції бази даних є прямо сумісними (forward-compatible) та оборотними, де це можливо.
- Запис/надсилання через постачальника залишаються вимкненими, доки не пройдуть докази синхронізації читання та ізоляції.
- Інтеграція Microsoft запускається лише після стабілізації шляху читання/синхронізації Google, якщо вона не ізольована за незалежним прапорцем.

## 9. Поточні перешкоди перед запуском живого Gmail

- виділений секрет шифрування поштової скриньки;
- точний стан верифікації екрана згоди та обмежених областей доступу Google;
- проєкт/тема/підписка Pub/Sub та аудиторія автентифікованого push-потоку;
- докази зовнішньої досяжності маршруту для push-запитів;
- еквівалентність надійної робоче середовище-БД/черги або керована інфраструктура;
- приймання власником у оглядачі Chrome.

Ці перешкоди не заважають реалізації чистих контрактів, тестів конвертів маркерів доступу, фундаменту черги з ізоляцією за власником та правдивих API готовності. Проте вони унеможливлюють чесне оголошення статусу `connected`.
