## 0. Висновок аудиту

В останній складанні вже існує багатоформатний і складний файловий перегляд. Тому стара ідея «створити PDF/Office/Archive-переглядачі з нуля» скасована. Визначення форматів і відмальовувачі **не перезаписували**. Від старого UFW v0.2 взято контракти й тести в ізольований `integrations/universal-file-workspace-core-v0.2/`, а інтеграційний шар v0.3 використовує наявні відмальовувачі.

Підтверджено кодом останнього архіву:

- `src/MailBijlageVoorbeeld.tsx` — великий диспетчер формату; окремі відмальовувачі PDF, DOCX, spreadsheet, presentation, archive, signature, media та спеціалізованих форматів.
- `src/MailBijlageVensters.tsx` — окремі draggable/resizable Mail-вікна із системою `platform/vensters`.
- `src/DriveBrowser.tsx` — Google Drive **вже повторно використовує** `loadMailAttachmentPreviewFromBlob` і `MailAttachmentPreviewBody`.
- `shared/bestandsformaten.ts` — спільна таксономія 13 файлових сімейств для UI.
- `src/platform/vensters.tsx` — єдиний менеджер вікон, док, пріоритети і геометрія.
- `src/mail-bijlage-lader.ts` — читання поштових вкладення chunks, обмеження 32 MiB, кеш та concurrency limit.
- `package.json` — вже містить pdfjs-dist, pdf-lib, officeparser, xlsx, fflate, tesseract.js та інші бібліотеки.

Увага: наявність вихідних модулів **не доводить**, що всі окремі формати працюють у реальному оглядачі і з реальним файлом. Такі сценарії мають окремі acceptance tests.

## 2. Контракт для інших компонентів

```tsx
import {openUniverseelBestand} from '../bestand/universeel-bestand';

// У конкретному сервісі спочатку перевірити сесію, owner/space, connector permission,
// account та відповідний provider authorization, отримати Blob через чинний backend.
openUniverseelBestand({
  bron: 'github', // також 'mail'|'google-drive'|'private-cloud'|'browser-file' та інші
  bestand: alreadyAuthorizedBlob,
  bestandsnaam: 'README.md',
  contentType: 'text/markdown',
  bronLabel: 'GitHub',
});
```

Не передавати OAuth секрет, token, cookie, signed URL, filesystem path чи довільну зовнішню адресу. Переглядач не має права самостійно скачувати URL із `intent`. Цей API виключно для Blob, який вже легітимно отриманий джерелом. Для серверних обробляти сценарії використання використати окремий перевірений ACL кінцева точка після наступного етапу.

## 4. Розподіл паралельних агентів

- **Агент A — inventory:** обов'язково перевірити всі сучасні `*Voorbeeld`, MIME/magic-byte, дозволи, кеш, асинхронні уривки, old попередній перегляд регресія. Нічого не переписувати.
- **Агент B — adapters:** джерела Google Drive, приватний Cloud, GitHub, OneDrive/Dropbox тільки там, де існують авторизовані постачальник кінцеві точки. Жодних raw URLs та маркерів доступу у клієнтському `FileRef`.
- **Агент C — UX:** інтеграційний `Venster`, режими narrow/мобільний/wide, джерело attribution, access стани, розміри, кілька вікон, клавіатура, screen readers і незайманий `CanonicalChrome`.
- **Агент D — engines/QA:** діагностувати фактичні попередній перегляд implementations, формати, шкідливі макроси/HTML/SVG, ZIP-bombs, резервний варіант та cap, ліцензійні обмеження; додати engine реєстр тільки після ідентифікації виконуваних пакетів.
- **Інтегратор:** власник єдиної базової гілки й випуск manifest, синхронізація злиття; жодне паралельне відгалуження не може замінити новіші робоче середовище-файли старими.
