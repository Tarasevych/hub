# Повна інтеграція Хмари M9 — каталоги S3/DAV та безпечні великі завантаження

**Основа:** ізольована копія `cloud-full-integration-m8`, що походить від `mijn-ruimte-20261027-212158`. Це ЛИШЕ ДЛЯ РОЗРОБКИ, не робоче середовище. Поточний стан робочого сервера після цього архіву не перевірений.

## Що справді створено

1. `backend/cloud-m9-xml.ts` — вузький структурний XML-аналізатор для метаданих з лімітами 1 MiB, 3000 вузлів, 24 рівні глибини, забороною DTD/ENTITY/CDATA/PI. Читає DAV multistatus та S3 XML за QName і URI простір імен. **Не замінює загальнопризначений повний XML-аналізатор**; потрібен незалежний огляд та provider-тестові зразки.
2. `backend/cloud-m9-directory.ts` — `NextcloudDirectory`, `S3CompatibleDirectory('s3')`, `S3CompatibleDirectory('backblaze-b2')`; серверні перевірені резолвери облікових записів; WebDAV PROPFIND Depth:1; AWS S3 ListObjectsV2 з SigV4 і B2 S3-compatible підмножина; `encoding-type=url`; відокремлені курсори S3; обмеження на розмір, DNS/SSRF для Nextcloud через зовнішню політику й захищену мережеву конфігурацію; `redirect:'error'`.
3. `backend/cloud-m9-directory-composition.ts` — фабрика для 11 типів каталогів із явним інжектуванням маркерів доступу, регіонів, облікових записів і вихідний трафік policy. Ця фабрика не додає автоматично маршрути у робоче середовище. Для роботи потрібен чинний M8 координатор + M4/M6 авторизація та перевірені облікові записи.
4. `backend/cloud-m9-upload-sessies.ts` — контрольована передача одного блока за раз Microsoft Graph і Dropbox; точний `Content-Range` / Dropbox зміщення; запити не надсилають Graph маркер доступу на вивантаження сеанс URL; стан `uploaded_not_verified` після кінцевого фіксації змін, не «успіх»; невизначений мережевий результат вимагає перевірки.
5. `backend/cloud-m9-checkpoints-pg.ts` і `migrations/0122_cloud_m9_upload_checkpoints.sql` — зашифровані на сервері сеанс спроможності, атомарний CAS по попередньому зміщення + власник/space/account/provider/source ревізія/тимчасове право, карантин прострочених оренд. Не запускати міграцію в робоче середовище без перевірки ролей і сумісності зі схемою.
6. Усунено нестабільність тестів M7 та M8: змінювання останнього символу base64url могло не змінити декодований байт. Зміна першого символу дає детерміновану перевірку пошкодження.
7. Сценарій `scripts/cloud-volledige-uitgave-poort.mjs` розширено з 73 до **84** live-критеріїв, статус продовжує `BLOCKED`.

## Межі безпеки та відкриті задачі

- Сервер може технічно мати доступ до OAuth-маркерів доступу і питомих незашифрованих файлів. AES-256-GCM шифрування вивантаження спроможність у PostgreSQL не є гарантією захисту від адміністратора з контролем сервера. Для приватного Сховище потрібні незалежний клієнт, перевірка походження коду, окрема модель відновлення ключів.
- Наступний етап має додати контрольовану перезвірку `nextExpectedRanges` та Dropbox зміщення із постачальниками після переривання, а не відновлюватися навмання. Прострочені тимчасове право нині лише карантинуються.
- Фоновий фоновий обробник, який створює вивантаження сеансу, читає великі файли потоково та зв'язує M9 з M4 account дозволи, ще **не під'єднаний**. М9 — стадійне ядро, не live файловий рушій.
- Кінцевий `uploaded_not_verified` має пройти незалежний read-back/контрольна сума і лише після цього може перейти до перевірений copy; оригінал не видаляти без умовного видалити із підтвердженим ревізія.
- Питомий `NextcloudTransport.stat` старого M3 використовує розбір WebDAV-XML регулярними виразами. Його необхідно перенести на перевірений XML-модуль до live-випуску. **Наявність M9-directory не усуває цей борг автоматично.**
- Довільні Nextcloud сервери потребують реального DNS rebind/SSRF міжмережевий екран на рівні мережі, не лише URL-перевірку.
- S3 pseudo-folders, B2 application-key restrictions, права SharePoint орендар та GitHub сховища мають залишатися provider-aware: не обіцяти недоступний функціонал.
- Повне мапування ACL, версій, спільного доступу, великих файлів для всіх 11 типів, багатовкладковий/browser синхронізація і UI Наскрізні ще не закрито. Публічний Cloud не активувати.

## Рекомендоване продовження (M10)

1. На окремому передпускове середовище з Node.js 24+ та тестовою PostgreSQL провести всі міграції M1–M9, відкочування та повний `npm ci; npm run typecheck:server; npm run build`.
2. Замінити M3 DAV regex-stat на структурний розбірник і виконати постачальник тестові зразки.
3. Під'єднати PostgreSQL сеанс контрольна точка до trust-scoped фоновий обробник, зашифрований сеанс початковий запуск, штучне сповільнення частоти/обмеження частоти запитів, повторна спроба policy та відновлення узгодження.
4. Авторизувати два різні облікові записи одного постачальника й провести реальні COPY з read-back SHA-256 та відкликання під час передачі; підтвердити move-конфлікти.
5. Перевірити обмін між оглядачами, вкладками і пристроями, роль технічного профілю і нуль витоків між користувачами.
6. Зовнішній крипто- й безпековий аудит. Лише після нього дозволити кандидат на один повний Cloud-випуск.
