# Повна інтеграція Хмари — M7: криптографічний захист власника даних

**28.10.2026 · ЛИШЕ ДЛЯ РОЗРОБКИ · заборона встановлення · base M6**

## 1. Непорушна межа довіри

**Акаунт користувача не може бути математичним секретним ключем сам по собі.** Ім'я, email, cookie, OAuth і навіть звичайний підпис passkey лише підтверджують особу; не слід виводити ключ шифрування із загальнодоступного account ID або пароля входу.

Приватні дані захищаються випадковим 256-бітним ключем, створеним **на пристрої**. Доступ до нього має власник через 256-бітний recovery секрет або, якщо доступна розширена функція WebAuthn PRF, через підтверджену PRF-відповідь відповідного passkey. Сервер отримує тільки зашифровану копію кореневого ключа. Акаунт прив'язує цей ключ до конкретного identity + space; **автентифікація і дешифрування — два різних чинники**.

**Важливе обмеження:** вебсервер, який контролює сторінку JS, теоретично може підмінити її, перехопити recovery secret/PRF виведення під час розблокування або прочитати розшифрований файл із пам'яті сторінки. Поки немає незалежно перевірюваного/підписаного клієнта, прозорості постачання коду, ізоляції від XSS та незалежного аудиту, **не можна гарантувати захист від зловмисного адміністратора з правом змінювати серверний код**. Навіть підпис JS не захищає від підміни HTML-сторінки, що вказує на інший скрипт, без окремої точки довіри.

## 2. ДВА режими, обидва з чесним поясненням

| | Приватний зашифрований Vault | Нативні файли Google/Dropbox/Microsoft тощо |
|---|---|---|
| Де шифрується | У довіреному клієнті **перед** завантаженням | У провайдера за його власними правилами |
| Що бачить наш сервер при COPY | Шифротекст, розмір, технічні ID, частоту запитів | Може обробляти відкриті байти та OAuth-токен під час BFF-операції |
| Провайдер бачить оригінал | Ні, тільки шифротекст (якщо файл завантажено саме в E2EE Vault) | Так, якщо це вихідний нативний файл |
| Попередній перегляд | Лише після розблокування у клієнті | Можливий нативний перегляд; залежить від API |
| Фонові передачі без користувача | Лише копіювання шифротексту (за умови попереднього дозволу) | Потребують делегованого доступу; не називати zero-knowledge |
| Поширення | Потрібна окрема клієнтська схема E2EE-шерингу та ключів адресатів | За правилами конкретного провайдера |
| Відновлення ключа | Тільки через user-owned recovery або підтримуваний passkey PRF | Не застосовується до нативного контенту провайдера |

## 3. Реалізовані модулі M7

- `src/cloud/versleutelde-kluis-m7.mjs` — WebCrypto AES-256-GCM, випадковий перефайловий DEK, AAD із `accountId + space + fileId + revision`, випадковий IV для кожної операції, шифрування імені/MIME у метаданих, SHA-256 зашифрованих частин; offline recovery через HKDF SHA-256 із 256-бітного випадкового recovery-secret; умовна прив'язка до попередньо **перевіреної** WebAuthn PRF-відповіді; потокове шифрування обмежених блоків (<=4 MiB).
- `backend/cloud-m7-blinde-overdracht.mjs` — переносить тільки `ufw-vault-v1` зашифровані блоки, stage -> verify -> publish, перевіряє власника/простір, повторює authorize на кожному блоці; **MOVE та видалення оригіналу відхиляються**; невизначений стан -> review, ніколи auto-delete. `target` реалізує абстрактний staging contract; реальні провайдерні адаптери ще потрібно підключити.
- `backend/cloud-m7-privacy-beleid.mjs` — чесна класифікація `encrypted_vault` та `provider_native`, відмова для нативних операцій E2EE Vault, які ще не підтримуються; для нативних файлів потрібна окрема user-presence lease.
- `backend/cloud-m7-sessie-lease.mjs` — обмеження owner/space/connection, операції, обсягу, терміну і користувач presence. **Не замінює справжньої серверної авторизації та не захищає від адміністратора з доступом до runtime.**
- `scripts/cloud-volledige-uitgave-poort.mjs` — додано 12 нових критичних блокерів. Без доказів повертає `BLOCKED`.

**Жоден із цих модулів не під'єднаний до публічного API або production OAuth-сховища.** Це свідомо: інтеграція в M4/M6 повинна пройти аудит ACL і меж довіри до активації.

## 4. Чому попереднє M4-зберігання OAuth токенів не є zero-knowledge

`backend/cloud-verbinding-m4-pg.ts` виконує AES-256-GCM із ключем `CLOUD_OAUTH_TOKEN_ENCRYPTION_KEY_V1` на сервері. Це захищає секрети у БД від багатьох атак, **але системний адміністратор з доступом до цього ключа або runtime може розшифрувати їх**. Тому допоки токени зберігаються за цією схемою, потрібна назва `server-managed delegated access`, а не `zero-knowledge`.

Майбутня більш сувора модель для приватних зв'язків: клієнтське запечатування refresh-token під користувач ключ; сервер зберігає тільки ciphertext; користувач розблоковує і делегує вузький короткий одноопераційний дозвіл для BFF. Деякі провайдери/браузери не підтримують прямий CORS та фоновий режим OAuth. Сервер **може отримати access token і вміст під час живого BFF-запиту**, тому сувору E2EE-гарантію слід давати лише приватному Vault, а не довільним нативним файлам.

## 5. Стійкість, швидкість, сумісність

- Файл ділиться на автентифіковані блоки до 4 MiB; за необхідності клієнт шифрує їх по одному без завантаження всього файла в RAM.
- UI може відобразити успішну **постановку в чергу** одразу після drag-and-drop, але не повинен показувати «Передано» до фактичного server verify і client verification.
- Server opaque COPY переносить зашифровані блоки, не дешифруючи; адаптери повинні підтримувати контрольований паралелізм, provider-specific rate limits, backpressure, стійку чергу PostgreSQL, ідемпотентність, перевірку ревізії і відкликання доступу під час передачі.
- API-провайдери (Drive/Graph/Dropbox/WebDAV/S3/Box/pCloud/GitHub) *не уніфікують* свою модель прав на 100%; capability engine повідомляє, які дії реально дозволені; не вигадувати функції.
- Якщо користувач хоче редагувати E2EE-файл у вебредакторі провайдера, він має тимчасово відкрити plaintext провайдеру або редагувати у нашому довіреному клієнті; приховати цю різницю не можна.

## 6. Обов'язковий безпека release gate

1. Незалежний криптоаудит (GCM nonce uniqueness, HKDF context separation, AAD/replay, повна коректність обробки потокових блоків).
2. Схема версіонування та *anti-rollback*: сервер не повинен непомітно підмінити файл старим, але валідним шифротекстом. Потрібен клієнтський контроль monotonic версія / підтверджені журнали.
3. Незалежна цілісність клієнта: підписаний застосунок/розширення або перевірюваний механізм постачання коду; CSP, Trusted Types, ізоляція origin, незалежний аудит XSS/supply chain.
4. WebAuthn PRF: жива перевірка конкретних браузерів і пристроїв; server-side WebAuthn assertion verification, UV=обов’язково, rpId/origin/challenge/credential binding. За відсутності PRF — офлайн recovery.
5. E2EE-шеринґ: перевірені ключі адресата, скасування доступу з перешифруванням для майбутнього доступу; не обіцяти відкликання вже розшифрованих копій.
6. Управління recovery й ротація ключів, тест відновлення на іншому пристрої. Без user-held ключа відновлення даних адміністраторами **не буде**.
7. Native провайдер token потік: постійне зберігання лише зафіксованого ciphertext там, де заявлено; заборона токенів у логах/URL; окреме тестування BFF під час делегованої сесії.
8. Перевірки на справжніх акаунтах кожного заявленого провайдера, реальні великі передачі з відмовами, throttling, повторна спроба, rate limits.
9. PostgreSQL staging, E2E Chrome/Firefox/Safari, multi-tab/multi-device, браузерний переглядач зашифрованих документів, доступність WCAG.
10. Node.js 24+ typecheck/build/E2E та 100% перевірка M1–M6 після інтеграції. Жодного `DEPLOY` до виконання всіх пунктів.

## 7. Умова готовності

M7 — **working cryptographic prototype та fail-closed server boundary**, а не підтверджений high-security production cryptosystem. Навіть успішні unit tests не замінюють незалежний аудит. Поточний release gate залишається `BLOCKED`.
