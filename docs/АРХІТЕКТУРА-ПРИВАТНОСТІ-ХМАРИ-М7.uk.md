# Повна інтеграція Хмари — M7: криптографічний захист власника даних

**28.10.2026 · ЛИШЕ ДЛЯ РОЗРОБКИ · заборона встановлення · base M6**

## 1. Непорушна межа довіри

**Обліковий запис користувача не може бути математичним секретним ключем сам по собі.** Ім'я, email, cookie, OAuth і навіть звичайний підпис ключ доступу лише підтверджують особу; не слід виводити ключ шифрування із загальнодоступного account ID або пароля входу.

Приватні дані захищаються випадковим 256-бітним ключем, створеним **на пристрої**. Доступ до нього має власник через 256-бітний таємниця відновлення або, якщо доступна розширена функція WebAuthn PRF, через підтверджену PRF-відповідь відповідного ключ доступу. Сервер отримує тільки зашифровану копію кореневого ключа. Обліковий запис прив'язує цей ключ до конкретного identity + space; **автентифікація і дешифрування — два різних чинники**.

**Важливе обмеження:** вебсервер, який контролює сторінку JS, теоретично може підмінити її, перехопити таємниця відновлення/PRF виведення під час розблокування або прочитати розшифрований файл із пам'яті сторінки. Поки немає незалежно перевірюваного/підписаного клієнта, прозорості постачання коду, ізоляції від XSS та незалежного аудиту, **не можна гарантувати захист від зловмисного адміністратора з правом змінювати серверний код**. Навіть підпис JS не захищає від підміни HTML-сторінки, що вказує на інший сценарій, без окремої точки довіри.

## 2. ДВА режими, обидва з чесним поясненням

| | Приватний зашифрований Сховище | Питомі файли Google/Dropbox/Microsoft тощо |
|---|---|---|
| Де шифрується | У довіреному клієнті **перед** завантаженням | У постачальника за його власними правилами |
| Що бачить наш сервер при COPY | Шифротекст, розмір, технічні ID, частоту запитів | Може обробляти відкриті байти та OAuth-маркер доступу під час BFF-операції |
| Постачальник бачить оригінал | Ні, тільки шифротекст (якщо файл завантажено саме в E2EE Сховище) | Так, якщо це вихідний питомий файл |
| Попередній перегляд | Лише після розблокування у клієнті | Можливий питомий перегляд; залежить від API |
| Фонові передачі без користувача | Лише копіювання шифротексту (за умови попереднього дозволу) | Потребують делегованого доступу; не називати нульове розголошення |
| Поширення | Потрібна окрема клієнтська схема E2EE-спільного доступу та ключів адресатів | За правилами конкретного постачальника |
| Відновлення ключа | Тільки через відновлення під контролем користувача або підтримуваний ключ доступу PRF | Не застосовується до питомого вмісту постачальника |

## 3. Реалізовані модулі M7

- `src/cloud/versleutelde-kluis-m7.mjs` — WebCrypto AES-256-GCM, випадковий перефайловий DEK, AAD із `accountId + space + fileId + revision`, випадковий IV для кожної операції, шифрування імені/MIME у метаданих, SHA-256 зашифрованих частин; поза мережею відновлення через HKDF SHA-256 із 256-бітного випадкового таємниця відновлення; умовна прив'язка до попередньо **перевіреної** WebAuthn PRF-відповіді; потокове шифрування обмежених блоків (<=4 MiB).
- `backend/cloud-m7-blinde-overdracht.mjs` — переносить тільки `ufw-vault-v1` зашифровані блоки, stage -> перевірка -> publish, перевіряє власника/простір, повторює authorize на кожному блоці; **MOVE та видалення оригіналу відхиляються**; невизначений стан -> review, ніколи auto-delete. `target` реалізує абстрактний передпускове середовище contract; реальні постачальницькі перехідники ще потрібно під'єднати.
- `backend/cloud-m7-privacy-beleid.mjs` — чесна класифікація `encrypted_vault` та `provider_native`, відмова для питомих операцій E2EE Сховище, які ще не підтримуються; для питомих файлів потрібна окрема тимчасове право присутності користувача.
- `backend/cloud-m7-sessie-lease.mjs` — обмеження власник/space/connection, операції, обсягу, терміну і користувач присутність. **Не замінює справжньої серверної авторизації та не захищає від адміністратора з доступом до середовище виконання.**
- `scripts/cloud-volledige-uitgave-poort.mjs` — додано 12 нових критичних перешкод. Без доказів повертає `BLOCKED`.

**Жоден із цих модулів не під'єднаний до публічного API або робоче середовище OAuth-сховища.** Це свідомо: інтеграція в M4/M6 повинна пройти аудит ACL і меж довіри до активації.

## 4. Чому попереднє M4-зберігання OAuth маркерів доступу не є нульове розголошення

`backend/cloud-verbinding-m4-pg.ts` виконує AES-256-GCM із ключем `CLOUD_OAUTH_TOKEN_ENCRYPTION_KEY_V1` на сервері. Це захищає секрети у БД від багатьох атак, **але системний адміністратор з доступом до цього ключа або середовище виконання може розшифрувати їх**. Тому допоки маркери доступу зберігаються за цією схемою, потрібна назва `server-managed delegated access`, а не `zero-knowledge`.

Майбутня більш сувора модель для приватних зв'язків: клієнтське запечатування маркер оновлення під користувач ключ; сервер зберігає тільки шифротекст; користувач розблоковує і делегує вузький короткий одноопераційний дозвіл для BFF. Деякі постачальники/оглядачі не підтримують прямий CORS та фоновий режим OAuth. Сервер **може отримати маркер доступу і вміст під час живого BFF-запиту**, тому сувору E2EE-гарантію слід давати лише приватному Сховище, а не довільним питомим файлам.

## 5. Стійкість, швидкість, сумісність

- Файл ділиться на автентифіковані блоки до 4 MiB; за необхідності клієнт шифрує їх по одному без завантаження всього файла в RAM.
- UI може відобразити успішну **постановку в чергу** одразу після перетягування мишею, але не повинен показувати «Передано» до фактичного server перевірка і client перевірка.
- Непрозоре серверне копіювання переносить зашифровані блоки, не дешифруючи; перехідники повинні підтримувати контрольований паралелізм, залежні від постачальника обмеження частоти запитів, зворотне стримування потоку, стійку чергу PostgreSQL, ідемпотентність, перевірку ревізії і відкликання доступу під час передачі.
- API-постачальники (Drive/Graph/Dropbox/WebDAV/S3/Box/pCloud/GitHub) *не уніфікують* свою модель прав на 100%; механізм спроможностей повідомляє, які дії реально дозволені; не вигадувати функції.
- Якщо користувач хоче редагувати E2EE-файл у вебредакторі постачальника, він має тимчасово відкрити відкритий текст постачальнику або редагувати у нашому довіреному клієнті; приховати цю різницю не можна.

## 6. Обов'язковий безпека випуск пропускний бар'єр

1. Незалежний криптоаудит (GCM nonce uniqueness, HKDF context separation, AAD/replay, повна коректність обробки потокових блоків).
2. Схема версіонування та *захист від відкочування версії*: сервер не повинен непомітно підмінити файл старим, але дійсним шифротекстом. Потрібен клієнтський контроль монотонний версія / підтверджені журнали.
3. Незалежна цілісність клієнта: підписаний застосунок/розширення або перевірюваний механізм постачання коду; CSP, Trusted Types, ізоляція origin, незалежний аудит XSS/ланцюг постачання.
4. WebAuthn PRF: жива перевірка конкретних оглядачів і пристроїв; серверний WebAuthn твердження перевірка, UV=обов’язково, rpId/origin/виклик перевірки/обліковий доказ binding. За відсутності PRF — поза мережею відновлення.
5. E2EE-спільний доступ: перевірені ключі адресата, скасування доступу з перешифруванням для майбутнього доступу; не обіцяти відкликання вже розшифрованих копій.
6. Управління відновлення й ротація ключів, тест відновлення на іншому пристрої. Без утримуваного користувачем ключа відновлення даних адміністраторами **не буде**.
7. Native постачальник token потік: постійне зберігання лише зафіксованого шифротекст там, де заявлено; заборона маркерів доступу у журналах/URL; окреме тестування BFF під час делегованої сеансу.
8. Перевірки на справжніх облікових записах кожного заявленого постачальника, реальні великі передачі з відмовами, штучне сповільнення частоти, повторна спроба, обмеження частоти запитів.
9. PostgreSQL передпускове середовище, Наскрізні Chrome/Firefox/Safari, багатовкладковий і багатопристроєвий режим, оглядачевий переглядач зашифрованих документів, доступність WCAG.
10. Node.js 24+ перевірка типів і складання/Наскрізні та 100% перевірка M1–M6 після інтеграції. Жодного `DEPLOY` до виконання всіх пунктів.

## 7. Умова готовності

M7 — **робочий криптографічний прототип та закриття при збої серверна межа**, а не підтверджений високозахищена робоче середовище криптосистема. Навіть успішні одиничні випробування не замінюють незалежний аудит. Поточний випуск пропускний бар'єр залишається `BLOCKED`.
