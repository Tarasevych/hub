# Нотатки з безпеки (`SECURITY-NOTES`)

Вихідне припущення: зловмисник знає повний вихідний код і всі старі секрети (із середовища AppDeploy).
**Ротуйте абсолютно все з [`ENV-VARS.uk.md`](./ENV-VARS.uk.md) / [`ENV-VARS.md`](./ENV-VARS.md) перед першим запуском у production.**

## 1. Статичний аудит (2026-10-02, на коді AppDeploy)
1. КРИТИЧНО: `POST /api/owner/security/session-fixture` створював сесію власника (`qaSynthetic`) без автентифікації.
2. КРИТИЧНО: `/api/owner/google-contour/reveal` повертав клієнтський секрет Google та ключ грантів у відкритому (читабельному) вигляді.
3. ВИСОКИЙ: `wrapKey` (google-contour) виводив ключ шифрування з клієнтського секрету OAuth.
4. ВИСОКИЙ: ключ сховища секретів (vault) мав резервний повернення стану (fallback) на інші ключі та клієнтські секрети.
5. СЕРЕДНІЙ: `MailComposeEditor.parseValue` використовував `innerHTML` на живому DOM-елементі.

Усі п'ять вразливостей усунено (спочатку за прапорцями конфігурації, а в self-hosted версії ці маршрути та код повністю видалено, див. §2).

## 2. Self-hosted версія: вирішено у фазі A та на кроці очищення
- Більше жодної платформи AppDeploy: власний Node-сервер (`server/start.ts`) за Cloudflare Tunnel, слухає виключно на `127.0.0.1`.
- Лише відомі імена хостів; заголовки `x-forwarded-host`, `forwarded` та `x-real-ip` від клієнта відкидаються; IP-адреса клієнта береться виключно з `cf-connecting-ip`.
- Куки (Cookies): `Domain=.tarasevych.com; Secure; HttpOnly; SameSite=Lax` (більше немає `SameSite=None`/`Partitioned`). Підтверджено власником: усі піддомени належать йому.
- CSP як HTTP-заголовок: `script-src 'self' 'wasm-unsafe-eval'` (необхідно для `sql.js`, `h5wasm` та `pdf.js`; **жодного** `'unsafe-eval'`, жодного `'unsafe-inline'` для скриптів), `frame-ancestors 'none'`, HSTS, `nosniff`.
- Файли `l002-diagnostic.json`, `*.map` та приховані файли (dotfiles) ніколи не роздаються (404), навіть якщо вони потрапляють у `dist/`.
- Видалено: технічний хост AppDeploy (`TECH_ORIGIN`), `OwnerTestApp`, QA-фікстури, інтеграційні лабораторії, `session-fixture`, `self-test`, технічний finalize-маршрут та QA-політику CSP з `'unsafe-inline' 'unsafe-eval'`.
- Вхід через Google завжди повертається на `https://id.tarasevych.com/`; після входу перенаправляє на `hub.tarasevych.com`. Білий список перенаправлень (redirect allow-list) містить лише `*.tarasevych.com`.
- Контур Google (Client ID / Secret) береться виключно зі змінних середовища (або захищеного сховища власника); старі значення у таблицях БД ігноруються.

## 4. Ще відкрито / свідомо залишено як особливості експлуатації
- **Фронтенд для step-up** (audit-fix 5): при `STEP_UP_REQUIRED` показується двомовний запит на код TOTP/Passkey або повторний вхід через Google (після чого дію потрібно повторити). Відновлення методів входу можливе через API та розділ «Способи входу».
- **Примусове увімкнення RLS**: вмикається командою `db-rollen-instellen.sh rls-aan`, щойно `app.rls_audit` залишається порожнім після кількох днів експлуатації (`RUNBOOK-FASE-2-3.md` §4–5).
- **`__Host-`-куки**: неможливі з поточним потоком входу між кількома хостами (див. §3d).
- **npm (лише залежності розробки)**: 5 попереджень у dev-залежностях через tailwind 3 (`braces`/`chokidar`/`micromatch`), не входять у production-бандл; зникають з оновленням tailwind.
- **Випадкове блокування власника**: адреса власника більше не є винятком. Розблокування від імені root: `runuser -u postgres -- psql -d mijnruimte -c "update app.records set data = jsonb_set(data, '{status}', '\"approved\"') where tbl = 'users' and lower(data->>'email') = lower('<OWNER_EMAIL>')"` (див. `deploy/RUNBOOK-AUDIT-FIXES.md`).
- **Вимкнена Google-ідентичність** залишається записом-надгробком (tombstone): через 7 днів той самий Google-обліковий запис можна повторно під'єднати лише після того, як адміністратор видалить стару ідентичність.
- **Рядки аудиту** в `app.audit` залишаються після остаточного видалення облікового запису (append-only; поле `details` може містити e-mail адреси або id). Очищення можливе лише через `audit_verwijderen`.
- Legacy-роль (до виконання `db-rollen-instellen.sh instellen`) може видаляти рядки аудиту, встановивши GUC `app.audit_verwijderen`; тригер запобігає лише випадковому видаленню.
- Вираз `ALTER ROLE … PASSWORD` може з'явитися в логах Postgres, якщо увімкнено `log_statement=all`.
- Наявні спільні посилання-запрошення, створені до фази 3, залишаються багаторазовими до закінчення терміну їхньої дії (макс. 7 днів).
- **WebAuthn/passkeys**: старі неверифіковані маршрути залишаються вимкненими (див. #7), і вхід виключно за допомогою passkey без першого фактора не використовується. Починаючи з гілки `aanmeldmethoden`, кожен користувач має справжні криптографічно верифіковані passkeys у «Способи входу» (`backend/toegangssleutels.ts`, міграція 0023 з RLS, `rpId: tarasevych.com`) для step-up; крім того, спеціально для **схвалення серверних оновлень та рішень** власником (гілка `passkey-schvalennya`) реалізовано власне WebAuthn-ядро без зовнішніх залежностей (`deploy/goedkeuring/webauthn-kern.mjs`; ES256/EdDSA/RS256, attestation `none`, UV обов'язковий), яке використовують як застосунок, так і root; root перевіряє підпис незалежно за файлом `/etc/mijn-ruimte/goedkeur-passkeys.json`. Див. `deploy/RUNBOOK-VEILIGE-UITROL.md` §13.
- Попередження `b4-important-free` у `src/mail-zijbalk-navigatie.css` та `src/mail-gesprek-bewerker.css` (l002-audit): походить з AppDeploy v56, не є проблемою безпеки.

## Робоче полотно Werkblad v3 (прапорець `werkblad-v3`, стандартно вимкнено) — 27.10.2026
- Усі дії запису v3 проходять через `POST /api/owner/hub/werkblad/v3/bewaren` (сесія + CSRF, як і решта `/api/owner/hub`),
  шухляда = `user_id + ruimte` із сесії (ніколи з тіла запиту), RLS на таблицях `werkblad_v3_lade`, `werkblad_layout`, `werkblad_items` (0114).
- Сервер нормалізує дані за реєстром (`REGISTER_V3_HAKEN`): жодних довільних URL, жодних невідомих id, жодних технічних елементів у
  приватному просторі, префікс `usr:` лише на наявному ярлику, піктограми лише з дозволеного набору, заголовки без `<>`; оптимістичне блокування (optimistic locking) на кожному шарі (409).
- Ярлики відкриваються виключно через канонічний маршрутизатор зі свіжою перевіркою прав; команди (`cmd:`) лише відкривають відповідний розділ
  (`?actie=<id>`) і нічого не виконують автоматично — надсилання чи видалення відбувається виключно на початковому місці з власним підтвердженням.
